## 2. Problem Statement

PRD-000 shipped a complete paywall *experience* — the gate component, the 4 UX states, the freemium layout, the env-flag toggle, the dev override, the OSS launch artifacts. What it doesn't have is **the actual transaction**. The "View plans" CTA opens a humorous placeholder dialog that explicitly says *"Real Stripe Checkout integration lands in PRD-001."*

Adopters reading the blueprint see the pattern but cannot run a real payment flow against it. Until they have a working end-to-end Stripe integration, they cannot:

- Validate the pattern works in their own Cloud Portal tenant with real test-mode card data
- Trust the abstraction boundaries hold under a real provider (would changing providers actually be one-file?)
- See the postMessage / polling fallback work against the real Cloud Portal iframe sandbox

PRD-001 closes that gap. After this PRD ships, the blueprint is a **fully working reference**, not a partial demo.

## 6. User Stories

### US-1 — Editor on tenant without subscription completes a purchase

**As an** editor on a tenant whose entitlement is `tenant_no_subscription`,
**when I** click "View plans" in the gated card,
**I want** Stripe Checkout to open in a new tab with the €0.99 Price preselected, complete the payment, and see my iframe automatically refresh to the welcome card.

**Acceptance criteria:**

- Click "View plans" → `/api/checkout` returns a `{ url }` within 2 seconds.
- `window.open(url, '_blank')` opens the new tab; Stripe Checkout renders with €0.99 + `automatic_tax` if enabled in dashboard.
- I complete payment using a test card; Stripe redirects to `/paywall-return?session_id=...`.
- `/paywall-return` attempts `window.opener.postMessage({ type: 'paywall:refresh' }, origin)`. **NOTE:** modern browsers default to `noopener` for new tabs from sandboxed iframes, so `window.opener` is frequently `null`; the postMessage path is best-effort sugar (see ADR-0014). Polling is the load-bearing path.
- The iframe's `useEntitlement` keeps polling `/api/entitlement` every 3 seconds (started at `window.open`). If postMessage arrives, it triggers an *immediate* poll — but polling does NOT stop on postMessage receipt; it stops only when `status === 'allowed'` is returned OR 30 seconds elapse.
- When polling sees `status === 'allowed'` (after the webhook completes its upsert), gate transitions to `allowed` state and dialog closes.
- Whole flow completes in < 30 seconds wall-clock from `window.open` to gate transition (Stripe webhook delivery is typically 5–10s; polling catches the change within the next 3s).
- A `tenants` row is upserted with my `marketplaceAppTenantId` (via webhook `checkout.session.completed` handler — Tranche B).

### US-2 — Iframe sandbox blocks postMessage; polling fallback succeeds

**As an** editor in a Cloud Portal iframe where `allow-popups-to-escape-sandbox` does not permit `window.opener.postMessage` (theoretical fallback case),
**when I** complete the same Stripe Checkout flow,
**I want** the iframe to detect entitlement change via polling fallback within 30 seconds without requiring me to refresh the page manually.

**Acceptance criteria:**

- `useEntitlement` starts a 3-second-interval poll of `/api/entitlement` immediately when `window.open(stripe-checkout-url)` is called.
- Poll continues for up to 30 seconds (10 polls).
- When `/api/entitlement` returns `{ status: 'allowed' }` (after webhook completes), iframe transitions to welcome card and polling stops.
- If 30 seconds elapse without status change, polling stops gracefully; user sees a non-blocking notification "Payment may take a moment — refresh the page if your access doesn't appear within a minute."
- No reliance on `window.opener`; pure timer-based.

### US-3 — Customer reinstalls the app; checkout doesn't orphan their Stripe Customer

**As an** editor whose tenant previously purchased the paywall-blueprint app and then uninstalled / reinstalled it,
**when I** attempt to checkout a second time (e.g., the reinstall changed `marketplaceAppTenantId`),
**I want** my existing Stripe Customer reused (not a new orphan Customer created) so my purchase history stays intact.

**Acceptance criteria:**

- `/api/checkout` first runs `stripe.customers.list({ email: host.user.email, limit: 10 })`.
- Filters returned Customers to those where `metadata.app_slug === 'paywall-blueprint'` (so an adopter's other Stripe-driven apps aren't accidentally clobbered).
- If 0 candidates → create new Customer with `metadata: { tenant_id: marketplaceAppTenantId, app_slug: 'paywall-blueprint' }`.
- If 1 candidate → update its `metadata.tenant_id` to current value, reuse.
- If N>1 candidates (e.g., racey concurrent creates from earlier sessions) → pick the **most-recently-created** one (`created` timestamp desc), update its `metadata.tenant_id`, reuse. Log a warning with the discarded Customer IDs for adopter to review.
- Tests cover all three branches (0, 1, N candidates) with stubbed `stripe.customers.list` returns.

### US-4 — Webhook idempotency under Stripe retries

**As the** webhook handler,
**when** Stripe re-fires an event (retry on 5xx, or "Send test webhook" duplicate),
**I want** to process the entitlement upsert once and acknowledge subsequent duplicates with 200 silently.

**Acceptance criteria:**

- `processed_events.event_id UNIQUE` constraint catches the duplicate.
- Handler attempts INSERT INTO `processed_events`; on `unique_violation`, returns 200 with no further processing.
- A Stripe "Send test webhook" duplicate (same `event.id`) results in identical `tenants` row state — no double-upsert.

### US-5 — Webhook signature mismatch is rejected

**As the** webhook handler,
**when** an event arrives without a valid `Stripe-Signature` header (or signed with a wrong secret),
**I want** to reject with **400 Bad Request** (Stripe convention; Stripe will NOT retry 4xx) and log the failure with the `[PaywallBlueprint]` prefix.

**Acceptance criteria:**

- Handler calls `stripe.webhooks.constructEvent(rawBody, sig, endpointSecret)`.
- Constructor throws → handler returns **400** (not 401 — Stripe's own docs recommend 400 for malformed/signature-failure events).
- `console.error('[PaywallBlueprint] webhook signature verification failed', err)` logged.
- No `processed_events` row written; no `tenants` upsert; safe failure mode.

### US-6 — Adopter forks the blueprint and ships with their own Stripe account

**As an** adopter who has forked the repo,
**when I** follow the README's "Stripe Setup" section,
**I want** to swap my own `STRIPE_*` env values into `.env.local` and have the entire flow work without code changes.

**Acceptance criteria:**

- README's Stripe Setup section is 6 numbered steps (Account → test mode → Product/Price → API keys → Webhook → optional Tax).
- All 4 new env vars (`STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `STRIPE_PRICE_ID`, `STRIPE_WEBHOOK_SIGNING_SECRET`) are documented with examples in `.env.example`.
- Test mode card numbers are explicitly listed.
- The `stripe listen --forward-to localhost:3000/api/webhooks/stripe` local-dev command is documented.
- An adopter starting from a fresh fork can complete the full setup in under 30 minutes of dashboard clicks + npm install + env-var paste.

## 7. Functional Requirements

### FR-1 — `StripeProvider` adapter

`src/lib/paywall/providers/StripeProvider.ts` implements `PaymentProvider` (already declared in `types.ts` since PRD-000). Constructor takes the secret key + price ID. Methods:

- `generateCheckoutUrl({ tenantId, userEmail, returnUrl })` — finds or creates Stripe Customer (orphan-recovery flow); creates Checkout Session (`mode: 'payment'`, single line item with `STRIPE_PRICE_ID`, `automatic_tax: { enabled: true }`, metadata `{ tenant_id: tenantId }`); returns `session.url`.
- `generatePortalUrl(...)` — throws "Not implemented in PRD-001; lands in PRD-003."
- `verifyWebhookSignature(rawBody, sig)` — wraps `stripe.webhooks.constructEvent`; returns the parsed Event or throws.
- `parseWebhookPayload(event)` — maps Stripe Event types to internal `EntitlementChange` shape.

### FR-2 — `/api/checkout` route

Next.js App Router route at `src/app/api/checkout/route.ts`. POST endpoint. Reads `tenantId` + `userEmail` from request body. Returns `{ url: string }` (200) or `{ error: string }` (4xx / 5xx). Uses `StripeProvider.generateCheckoutUrl`. CORS / origin verification per `sitecore:marketplace-sdk-testing-debug` § 4.

**Stripe error translation (user-friendly messages):** Stripe SDK errors are developer-facing by default. The route MUST map known Stripe error codes to user-friendly messages before returning:

| Stripe error code | User-facing message | HTTP status |
|------|-----------|-------------|
| `tax_settings_not_set` (or any `tax_*` family) | `"Payment is being set up — please contact your administrator."` | 503 |
| `resource_missing` on the Price ID | `"This blueprint's checkout configuration is incomplete. Please contact your administrator."` | 503 |
| `rate_limit` | `"Payment service is busy — please try again in a moment."` | 429 |
| `api_connection_error` / `api_error` | `"Payment service is temporarily unavailable. Please try again."` | 503 |
| Any other Stripe error | `"Payment setup error — please contact your administrator."` + `console.error` with full Stripe error for adopters' logs | 503 |

The dialog's failure path (FR-8 below) renders the user-facing message inline.

### FR-3 — `/api/portal` route (PRD-001 stub)

POST endpoint at `src/app/api/portal/route.ts`. Returns `501 Not Implemented` with `{ error: 'Customer Portal lands in PRD-003. See README.' }`. Skeleton ensures PRD-003 wires in without inventing a route.

### FR-4 — `/api/entitlement` route

GET endpoint at `src/app/api/entitlement/route.ts`. Query params: `tenantId` (required), optionally `userId`. Returns `EntitlementResult` JSON identical to `SupabaseStore.getEntitlement`. Supports the polling fallback (client polls every 3s for up to 30s). Service-role Supabase client (not anon) — runs server-side per ADR-0009 + PRD-001 NFR-5.

### FR-5 — `/api/webhooks/stripe` route

POST endpoint at `src/app/api/webhooks/stripe/route.ts`. Reads raw request body (required for signature verification). Calls `StripeProvider.verifyWebhookSignature`; on failure → 401. On success: INSERT INTO `processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING`; if conflict → 200 silent. Otherwise dispatch:

| Stripe event | Action |
|--------------|--------|
| `checkout.session.completed` | UPSERT `tenants(tenant_id=metadata.tenant_id, stripe_customer_id, status='active', period_end=NULL, plan='premium')` |
| `customer.subscription.created` | UPSERT `tenants(... subscription_id, period_end)` (forward-compat — not fired by one-time Checkout) |
| `customer.subscription.updated` | Update `plan`, `seats_total`, `status`, `period_end` |
| `customer.subscription.deleted` | SET `status='cancelled'`; keep `period_end` |
| `invoice.payment_failed` | SET `status='past_due'`; optional grace period |
| `invoice.payment_succeeded` | Sanity-update `period_end` |

All upserts run in a transaction; webhook handler exits in ≤ 5 seconds (NFR-3).

**Unhandled event fall-through:** any Stripe event NOT in the 6-type table above (e.g., `charge.refunded`, `customer.deleted`, `payment_method.attached`, etc.) gets logged with the `[PaywallBlueprint]` prefix and returns **200 silently**. Rationale: Stripe sends many event types we don't care about by default (especially in test mode where adopters trigger refunds during their own dev cycles); returning 200 acknowledges the delivery without triggering retries. **Adopters who want refund handling add a `charge.refunded` handler** that sets `tenants.status = 'cancelled'` — README documents the extension point.

### FR-6 — `/paywall-return` page

Client component at `src/app/paywall-return/page.tsx`. Reads `session_id` query param. Renders a small Blok-styled "Confirming your access..." card. On mount:

```typescript
if (window.opener && !window.opener.closed) {
  window.opener.postMessage(
    { type: 'paywall:refresh', sessionId },
    appOrigin
  );
  // close window after small delay so the message is received
  setTimeout(() => window.close(), 500);
} else {
  // popup detached or sandbox-blocked; rely on polling
  setSessionStorageFlag();
}
```

Also writes `sessionStorage['paywall:lastCheckoutCompleted']` as a secondary signal the iframe poll can detect.

### FR-7 — `useEntitlement` hook

`src/lib/paywall/hooks/useEntitlement.ts`. Returns `{ entitlement, isLoading, triggerCheckout, error }`. `triggerCheckout()`:

1. POSTs to `/api/checkout` with current `tenantId` + `userEmail`. On 4xx/5xx response → set `error` state, return early (FR-2 maps Stripe errors to user-friendly messages already).
2. Opens `result.url` via `window.open(url, '_blank')`.
3. **Polls `/api/entitlement` every 3 seconds for up to 30 seconds** as the load-bearing path (see ADR-0014 — `window.opener` is frequently `null` from sandboxed iframes).
4. **In parallel**, listens for `postMessage({ type: 'paywall:refresh' })` from the new tab. If received, triggers an *immediate* poll (resets the next-poll-due timer to now); does NOT stop polling.
5. Polling stops when either: `/api/entitlement` returns `status === 'allowed'` (success) OR 30 seconds total elapse from `window.open` (timeout).
6. **Atomicity:** single `useState<EntitlementChangeSignal | null>` that any signal (postMessage handler OR poll handler) sets via `setState((prev) => prev ?? signal)` — first signal wins, subsequent are no-ops. Both listener and interval `clear` on first non-null state.
7. Returns to caller with success / timeout / error outcome via the `entitlement` + `error` state fields.

`PaywallCheckoutDialog` consumes the hook; replaces the placeholder "Got it" button with a real "Subscribe — €0.99 lifetime" button bound to `triggerCheckout`.

### FR-8 — `PaywallCheckoutDialog` rewire

Updated dialog at `src/lib/paywall/PaywallCheckoutDialog.tsx`. Replace placeholder copy + "Got it" button:

- New body: "One-time €0.99 payment. Unlimited seats. Lifetime access to the premium section."
- Footer: "Subscribe — €0.99" button (calls `useEntitlement().triggerCheckout()`) + "Cancel" button.
- During in-flight checkout: button shows spinner; both disabled.
- On success: dialog auto-closes; iframe transitions to welcome.
- On 30-second polling timeout: button shows "Tap to refresh" + non-blocking error toast.

The locked banner copy from ADR-0004 (`"Paywall disabled — demo mode"`) stays untouched — env-flag behavior is orthogonal to Stripe.

## 8. Non-Functional Requirements

### NFR-1 — Webhook signature verification (mandatory)

Every webhook POST MUST be verified via `stripe.webhooks.constructEvent(rawBody, sig, endpointSecret)`. Unsigned or wrong-signed events → 401. **No exception.** Per research § 8.3.

### NFR-2 — Webhook idempotency

`processed_events.event_id` is `UNIQUE`; INSERT ON CONFLICT DO NOTHING returns the silent-200 path. Replay safety required for Stripe retry behavior.

### NFR-3 — Webhook handler latency budget

Webhook handler MUST complete in ≤ 5 seconds (Stripe retries on >5s by default). Includes DB upsert. No external API calls in the hot path beyond the single Supabase upsert.

### NFR-4 — `/api/checkout` latency

`/api/checkout` MUST return a `{ url }` in ≤ 2 seconds under normal Stripe API response times. Customer-lookup-before-create adds ~200-400ms. Timeout handling: if Stripe API returns >2s, return 503 + retry guidance to client.

### NFR-5 — Polling cap

`useEntitlement` polling: max 30 seconds, 3-second interval, 10 polls. Polling MUST NOT continue after the dialog is closed or the gate transitions to allowed.

### NFR-6 — Security: server-only env vars

`STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SIGNING_SECRET` MUST be server-only (no `NEXT_PUBLIC_` prefix). `STRIPE_PRICE_ID` is operationally non-sensitive but server-only by convention. `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` is client-readable (intentional).

### NFR-7 — Server-side `/api/entitlement` uses service-role Supabase client; **unauthenticated in v1** (PRD-002 hardens)

The server route runs the entitlement check using `SUPABASE_SECRET_KEY` (service-role) — not the anon key. The route accepts `tenantId` as a query parameter and returns that tenant's entitlement.

**Known v1 limitation:** the route is unauthenticated. Any caller can query any `tenantId` and learn whether that tenant has an active subscription. Entitlement is a boolean (not sensitive in itself), but this is a **fingerprinting / enumeration leak** — an attacker could probe a list of `marketplaceAppTenantId` values to learn which orgs are paying customers.

**Acceptance for PRD-001:** README explicitly documents this under "Known limitations of v1 / Adopter responsibilities":

> ⚠ `/api/entitlement` in v1 is unauthenticated. Adopters using this blueprint for production-sensitive tenant lists should add a per-route auth check (e.g., verify a JWT signed with the iframe's Auth0 session) before going live. PRD-002 hardens this with `host.user.sub` verification against the requested `tenantId`.

**Why not fix in PRD-001:** the auth model for `/api/entitlement` overlaps with PRD-002's per-user seat enforcement (both need to verify `host.user.sub` against the requesting tenant's seat list). Doing it once cleanly in PRD-002 is better than two iterations.

### NFR-8 — Tests

- Unit tests for `StripeProvider` methods (stubbed `stripe` SDK).
- Integration tests for each API route (using `next-test-api-route-handler` or similar).
- Integration test for the orphan-recovery flow (US-3).
- Integration test for webhook idempotency (US-4).
- Integration test for signature failure rejection (US-5).
- Existing 74 tests continue to pass.

### NFR-9 — Stripe Tax (one-line enable)

PRD-001 ships with `automatic_tax: { enabled: true }` in the Checkout Session config. If the operator's Stripe dashboard does not have Tax enabled, Stripe returns a calculation error → checkout fails with a clear message → README troubleshooting section explains how to enable.

## 11. UX Considerations

### Flow diagram (Tranche C smoke walkthrough)

```
[Editor opens app, tenant has no subscription]
  → Gate evaluates → tenants row not active → renders NoSubscriptionState
  → [Editor clicks "View plans"]
  → PaywallCheckoutDialog opens with "Subscribe — €0.99 lifetime" button
  → [Editor clicks "Subscribe — €0.99 lifetime"]
  → POST /api/checkout {tenantId, userEmail}
  → Server: orphan recovery → Customer; Checkout Session create; return { url }
  → useEntitlement: window.open(url, '_blank')
  → New tab: Stripe Checkout renders €0.99 + (optional) tax
  → [Editor pays with 4242 4242 4242 4242 / any future expiry / any CVC]
  → Stripe redirects to /paywall-return?session_id=...
  → /paywall-return: window.opener.postMessage('paywall:refresh', origin) → window.close()
  → ALSO: Stripe webhook fires checkout.session.completed
       → /api/webhooks/stripe: verify sig → idempotency check → upsert tenants row → 200
  → Iframe: useEntitlement receives postMessage → re-runs getEntitlement → status='allowed'
  → Gate transitions to AllowedState → editor sees welcome card
[All within ~10-30 seconds wall-clock]
```

### Iframe success-return — polling is primary; postMessage is fastest-path-when-available

**Updated framing post-critical-review (ADR-0014 reframe):** In modern browsers (Chrome 88+, Firefox 79+, Safari recent), opening a new tab via `window.open()` from a **sandboxed iframe** defaults the new tab to `noopener` — meaning `window.opener` in the new tab is **`null`**. Cloud Portal's iframe sandbox attributes (`allow-popups`, `allow-popups-to-escape-sandbox`) permit the popup but don't necessarily preserve the opener reference.

**Realistic behavior:**

- **Polling is the load-bearing path.** `useEntitlement` starts a 3-second-interval poll of `/api/entitlement` immediately when `window.open(stripe-checkout-url)` is called. Polls for up to 30 seconds (10 polls) — bounded by Stripe's documented 95th-percentile webhook delivery latency.
- **postMessage is fastest-path sugar.** If the browser happens to allow `window.opener.postMessage`, the `/paywall-return` page sends a `paywall:refresh` message → the iframe's listener triggers an *immediate* poll (resets the next-poll-due timer to now) → next poll likely succeeds within ~1 second instead of waiting for the natural 3-second cadence.
- Both run in parallel; the polling path completes the transition regardless of postMessage success.

The `/paywall-return` page also writes a `sessionStorage` flag as a *secondary* signal — but cross-tab `sessionStorage` is also commonly blocked by sandboxed iframes, so this is even more best-effort than postMessage. Polling remains the contract.

## 13. Risks and Mitigations

### R1 — Scaffold migration 4a → 4b regression

**Risk:** The migration adds API routes but might require changes to `next.config.mjs` / CSP headers that affect the existing iframe behavior.

**Mitigation:** Migrate in Tranche A with the existing 74 tests as a regression net. Real-tenant iframe verification gate at the end of Tranche A before any new feature code lands.

### R2 — Cloud Portal iframe sandbox blocks postMessage

**Risk:** `window.opener.postMessage` from the new-tab `/paywall-return` page may fail under Cloud Portal's iframe sandbox (`allow-popups-to-escape-sandbox` may or may not propagate).

**Mitigation:** ADR-0014 specifies postMessage primary + polling fallback. Polling runs in parallel; iframe doesn't depend on postMessage to work.

### R3 — Concurrent checkout race conditions

**Risk:** Two editors on the same tenant click "Subscribe" simultaneously. Both `/api/checkout` calls may try to create new Stripe Customers (orphan recovery sees neither yet exists).

**Mitigation:** Stripe's idempotency keys can be used (`stripe.checkout.sessions.create({}, { idempotencyKey: tenantId })`); or simply accept that two Customers may be created in this race and the webhook idempotency will reconcile them. PRD-001 ships with idempotency keys per checkout request.

### R4 — Stripe webhook delivery delays

**Risk:** Stripe webhook delivery can lag by 5-30 seconds. Polling cap of 30 seconds (NFR-5) may time out before webhook completes for slow paths.

**Mitigation:** 30 seconds is Stripe's documented 95th-percentile delivery latency. If the operator hits this in test mode, we can extend to 60 seconds. Polling timeout shows a non-blocking "May take a moment" toast and the user can refresh manually.

### R5 — Stripe Tax misconfiguration

**Risk:** `automatic_tax: { enabled: true }` is shipped by default; if the operator's Stripe dashboard doesn't have Tax enabled, Checkout creation fails.

**Mitigation:** README explicitly documents the Stripe Dashboard → Settings → Tax flow. The Checkout Session creation error returns a clear message ("Stripe Tax is not enabled — visit dashboard to configure or set `automatic_tax: { enabled: false }` in `StripeProvider.ts`"). Adopters can disable Tax with a one-line change.

### R6 — Server-only env vars accidentally exposed client-side

**Risk:** `STRIPE_SECRET_KEY` or `STRIPE_WEBHOOK_SIGNING_SECRET` accidentally leak to the client bundle (e.g., wrong import in a client component).

**Mitigation:** NFR-6 + `.env.example` comments explicitly mark them server-only. Tranche B includes a build-time grep test (similar to T045's DCE grep) that scans `.next/static/` for these literals and fails the build if found.
