## 1. Idea Summary

A **public OSS reference Sitecore Marketplace App** that demonstrates how to integrate a paywall into a Marketplace App end-to-end — tenant entitlement check, per-user seat enforcement, self-service purchase / upgrade flow, license sync via provider webhooks — packaged as **a complete worked example** that other Marketplace developers can fork and adapt. The app itself has no real feature; it is purely demonstrative — the *paywall flow* IS the feature. The deliverable is a real installable Cloud Portal Marketplace app on the **SitecoreAI Full Screen** extension point that shows a freemium pattern (free piece + gated premium piece on one page) plus the four denial UX states (no-sub / seats-full / unassigned / allowed), all driven by a `<PaywallGate>` React wrapper and an entitlement store. Two clean abstraction boundaries (provider adapter + entitlement-store adapter) make Lemon Squeezy and Supabase Postgres swappable v1 worked examples rather than locked-in dependencies.

## 2. Problem Statement

Sitecore's Marketplace today provides **no built-in commerce primitives**. Every team that wants to charge for a Marketplace App — whether freemium or fully paid — starts from zero on every decision: which payment provider, how to map Cloud Portal tenants to subscription objects, how to enforce seats inside an iframe sandbox, what to show editors when access is denied, how to handle reinstalls, what to do when the payments provider is down, how to wire webhooks back to entitlements. The result is that the Marketplace ecosystem stays **free-only** because monetization is too painful to invent solo. A **vendor-neutral, opinionated, public worked example** removes that barrier: adopters fork the repo, swap the placeholder feature for theirs, change a few env vars, and ship a monetized Marketplace app — without inventing the gating pattern from scratch.

## 3. Target Users

**Primary:**

- **Marketplace App developers** (independent vendors + agencies + partner studios) who want to ship a freemium or paid Marketplace App but don't want to build the paywall plumbing. They consume this product by reading the README, browsing the repo, and copying the pattern (or forking the repo) into their own app.
- **hahnsolo's own future Marketplace apps** — this blueprint is also the reusable foundation for any hahnsolo app that wants commercial gating (Component Usage Atlas Pro, Redirect Manager Pro, future apps).

**Secondary (experienced indirectly via the reference app's UX):**

- **Editors / content authors** using a paywalled Marketplace App on their tenant — they encounter the gate, see the denial states, click through to purchase, return with access. They are the "user the gate is shown to" — the reference app's UX choices (copy, calls to action, banner styling) become the de-facto pattern adopters inherit.
- **Tenant admins** managing subscriptions — invite/revoke seats, change plan, view invoices (becomes real in PRD-002 / PRD-003).

## 4. Proposed Solution

A **public GitHub repository** containing a fully-functional Sitecore Marketplace App built on Next.js + the Marketplace SDK, deployed to Vercel, with all paywall plumbing cleanly factored behind two abstraction interfaces:

1. **Provider Adapter** — a single TypeScript interface (`PaymentProvider`) implemented by `LemonSqueezyAdapter` in v1. Implementations cover: generate purchase URL, verify webhook signature, parse webhook payload into `EntitlementChange` events. Swapping providers (Stripe, Paddle, Polar.sh) is a single new adapter file.
2. **Entitlement Store Adapter** — a single TypeScript interface (`EntitlementStore`) implemented by `SupabaseStore` in v1. Implementations cover: `getEntitlement(tenantId, userId)`, `upsertTenant(...)`, `upsertSeat(...)`, `recordPurchaseEvent(...)`. Swapping stores (Postgres, Upstash, Firestore) is a single new adapter file.

The runtime gate is a **React component** (`<PaywallGate>`) that wraps any subtree. On mount, it reads `application.context` from the Marketplace SDK (tenant id + user id), calls the entitlement store, and resolves to one of four UX states:

- **Allowed** — renders children. (In the reference app: a context-grounded "Welcome [user.name] to tenant [tenant.name] — your plan is [plan], [N/M] seats used" screen demonstrating the gate-aware authenticated session works.)
- **No subscription** — "Start your subscription / View plans" screen with a CTA to the provider's checkout (placeholder URL in PRD-000; real Lemon Squeezy URL in PRD-001).
- **Seats full** — "5/5 seats used. Upgrade or ask an admin to free up a seat" with both CTAs.
- **Unassigned** — "Your admin hasn't given you access yet" with a "Request seat" action (notification flow lands in PRD-002).

A single environment variable `NEXT_PUBLIC_PAYWALL_ENABLED` flips the entire gate between **enforced mode** (above behavior) and **demo mode** (children render verbatim PLUS a small persistent banner reading "Paywall disabled — demo mode"). The signaled-pass-through (banner visible) is intentional — it makes the env-flag's effect visible in the demo video and keeps the OSS / self-hosted fork story honest.

A dev-override environment variable `PAYWALL_DEV_OVERRIDE_USER_ID=<user-id>` lets local developers bypass the gate without polluting the entitlement store.

The **reference app's UI** is intentionally simple: a single-page layout with two visually-distinct sections — **top section is free** (rendered for everyone, even when paywall is enforced and the viewer is unauthorized — demonstrating "this part is yours") and **bottom section is gated** by `<PaywallGate>` (demonstrating "this part needs payment"). Both sections are visible without clicking, making the freemium pattern obvious in a single screen.

## 5. Value Proposition

- **For the Marketplace ecosystem:** Lowers the bar from "I'd have to invent a paywall from scratch" to "I fork this repo and replace one component." Unlocks the first wave of paid / freemium Marketplace apps that aren't viable today. Becomes the de-facto pattern other Marketplace builders point to.
- **For hahnsolo specifically:** Provides the commercial-gating foundation for *all future hahnsolo Marketplace apps* — Component Usage Atlas Pro, Redirect Manager Pro, etc. — without inventing the plumbing each time. Establishes hahnsolo as the operator who solved a meta-problem for the Sitecore Marketplace.
- **For the launch / OSS surface:** Strong public-Marketplace candidate. The narrative is clean and aspirational — "we made it easy to charge for your Marketplace App." A README + walkthrough video + public GitHub repo + Marketplace-listed reference app gives marketers, dev-rel, and platform-team voices a concrete reference to share.

## 6. Core Features

1. **`<PaywallGate>` React wrapper** with hooks (`useEntitlement`, `useSeat`, `usePurchaseUrl`) and four UX states.
2. **Entitlement-store adapter interface** + Supabase Postgres implementation. Schema: `tenants`, `seats`, `purchase_events`.
3. **Provider adapter interface** + (PRD-001) Lemon Squeezy implementation. Webhook handler that upserts entitlements idempotently on `provider_event_id`.
4. **Reference Marketplace app** on SitecoreAI Full Screen extension point. Single page; top section free; bottom section gated; freemium pattern visible at a glance.
5. **Context-grounded "Welcome" screen** (post-gate) using `application.context` — proves the gate-aware authenticated session works end-to-end.
6. **Env-flag toggle** (`NEXT_PUBLIC_PAYWALL_ENABLED`) with signaled demo-mode banner.
7. **Dev override** (`PAYWALL_DEV_OVERRIDE_USER_ID`) for local development bypass.
8. **README + walkthrough** explaining the pattern, the two adapter interfaces, the env-flag, and how to swap providers / stores.
9. **(PRD-002+)** Standalone admin view for seat management: invite, revoke, view who's using which seat.
10. **(PRD-003+)** Self-service customer portal embedded inside the Standalone view.

## 8. Assumptions

- **A1 — `application.context.tenantId` is durable across reinstalls.** If the same app is uninstalled and reinstalled on the same tenant, the SDK-reported tenant id stays stable. Risk: orphaned entitlement records if false. **Probe before PRD-001** (real-tenant test or SDK Sandbox once that exists).
- **A2 — `application.context` exposes a stable user identity (id, possibly email).** Seat tracking needs a stable id; email is the human-readable label. Assumed yes. **Probe before PRD-001.**
- **A3 — Lemon Squeezy as merchant of record is acceptable under Sitecore Marketplace ToS.** No legal blocker on a third-party merchant-of-record provider. **Legal review pre-PRD-001.**
- **A4 — Deployment target is Vercel** (consistent with other hahnsolo Marketplace apps). Confirm at PRD-000 kickoff if any reason to deviate.
- **A5 — Supabase free tier is sufficient for PRD-000–PRD-002.** Schema is small (3 tables); volumes are low. Confirm if real installs push into paid tier.
- **A6 — Webhook delivery from Lemon Squeezy to a Next.js API route on Vercel works without special obstacle.** Standard webhook pattern; Lemon Squeezy retries on 5xx; idempotency via `provider_event_id`. Verify in PRD-001 smoke.

## 9. High-Level Technical Considerations

- **Language / framework:** TypeScript + Next.js App Router (consistent with hahnsolo Marketplace apps).
- **SDK surfaces consumed in PRD-000:** `@sitecore-marketplace-sdk/client` for `application.context` only. No XMC calls, no Authoring GraphQL, no Edge GraphQL. PRD-000 is a low-SDK-risk scaffold — most logic is the gate + the store, not Sitecore plumbing.
- **Marketplace extension point:** SitecoreAI Full Screen (primary). Standalone (Cloud Portal Apps tab) added in PRD-002 for the admin view. Dashboard Widget added in PRD-002+ for the "Your plan" tile (deferred / optional).
- **Two abstraction boundaries (first-class):**
  - `PaymentProvider` interface — generate purchase URL, verify webhook, parse webhook → `EntitlementChange`.
  - `EntitlementStore` interface — getEntitlement, upsertTenant, upsertSeat, recordPurchaseEvent.
- **Concrete v1 implementations:** `LemonSqueezyAdapter` (PRD-001), `SupabaseStore` (PRD-000).
- **Entitlement state machine (returned by `getEntitlement(tenantId, userId)`):** `allowed | tenant_no_subscription | tenant_active_seats_full | tenant_active_user_unassigned | provider_unreachable`. Each maps to one of four UX states in `<PaywallGate>`.
- **Env-flag** evaluated at compile time (`NEXT_PUBLIC_*` prefix exposes to client bundle). When `false`, the gate component short-circuits to children + banner with zero entitlement-store call.
- **Dev override** is server-side preferred (server-only env var) to avoid leaking override to client bundles in production. Architecture stage should confirm the cleanest split.
- **Database schema (Supabase Postgres):**
  - `tenants(tenant_id PK, subscription_id, plan, seats_total, status, period_end)`
  - `seats(tenant_id FK, user_id, assigned_at, last_seen_at, PRIMARY KEY (tenant_id, user_id))`
  - `purchase_events(id PK, tenant_id, provider_event_id UNIQUE, raw_payload jsonb, processed_at)` — uniqueness on `provider_event_id` for webhook idempotency.
- **Webhook handler** (PRD-001) is a Next.js API route that verifies signature, looks up `provider_event_id` in `purchase_events` (idempotency), upserts `tenants` + `seats` rows, returns 200.
- **Deployment:** Vercel for the Next.js app; Supabase for Postgres; Lemon Squeezy for payments. All three are managed services; no own infrastructure.
- **Hosting expectations for adopters:** README documents the swap points — any Next.js host (Vercel / Netlify / self-hosted), any Postgres-or-similar store (via the `EntitlementStore` adapter), any merchant (via the `PaymentProvider` adapter).
- **Smoke test surface (PRD-000):** Install the app on a real Sitecore tenant; with Supabase entitlement table manually seeded, walk through all four UX states (allowed via seeded row, no-sub via deleted row, seats-full via `seats_total=1` already taken, unassigned via tenant-without-this-user-seat); screenshot each state.

## 10. Risks

- **R1 — `application.context` shape assumptions wrong.** If tenant id is not durable across reinstalls (A1) or user identity is not stable (A2), the entitlement model needs rework. **Mitigation:** real-tenant probe (or SDK Sandbox detour) before PRD-001. Operator has approved pausing for a Sandbox detour if this is a hard blocker.
- **R2 — Marketplace ToS prohibits external merchant-of-record providers** (A3). Forces self-merchant model (Stripe direct + Stripe Tax). Adds tax/VAT complexity. **Mitigation:** legal review pre-PRD-001; provider adapter abstraction means Stripe is one new file if forced.
- **R3 — Webhook delivery from Lemon Squeezy to Vercel-hosted Next.js API route hits an unexpected obstacle** (rate limit, signature scheme mismatch, cold-start timeout). **Mitigation:** PRD-001 smoke validates the round-trip in Lemon Squeezy sandbox + Supabase before going live.
- **R4 — Scope creep within PRD-000 from the freemium pattern.** Adding the freemium-within-app demo (D9) expanded PRD-000 from "gate + 4 states + ref app shell" to "gate + 4 states + ref app shell with two distinct sections + post-gate context-grounded screen." Could overrun the 1–2-day estimate. **Mitigation:** Keep the free section deliberately minimal (one paragraph + one mock UI element); resist adding any logic to it.
- **R5 — Public OSS expectations.** Once the repo is public, the community may ask for a second provider adapter (Stripe / Paddle) before PRD-001's Lemon Squeezy adapter is even stable. **Mitigation:** README explicitly signals "v1 = Lemon Squeezy; second provider after PRD-003." Issue triage SLA can be informal early.
- **R6 — `<PaywallGate>` reads context inside a Marketplace iframe whose mount lifecycle matters.** If `application.context` is not ready on first render, gate behavior on initial mount needs a loading state. **Mitigation:** architecture stage documents the loading-state UX (skeleton vs spinner vs gate-not-yet-rendered).
- **R7 — Demo-mode banner (D5) interferes with the post-gate screen visually.** A persistent banner on top of a context-grounded "Welcome" screen could look cluttered. **Mitigation:** UI design stage validates the layout; the banner is small and dismissible-during-session is an option.

## 11. Open Questions

(Parked for later PRDs or for operator action between phases. Each is a real outstanding decision, not an assumption.)

- **OQ1 — Trial mode** (PRD-001 design decision). Lemon Squeezy supports free trials natively (first N days free, then paywall kicks in). Build into `<PaywallGate>` from PRD-001 or defer to PRD-002? Affects state machine ("trialing" as a 5th state?).
- **OQ2 — Fail-open vs fail-closed when provider unreachable** (PRD-001). Lean fail-open with cached last-known entitlement + stale-after-N-hours warning, but operator-configurable. Defaults?
- **OQ3 — Marketplace public-listing submission** (post-PRD-000 stretch). Public GitHub is in scope; submitting the reference app to the Sitecore Cloud Portal Marketplace as a public-installable app is a separate process with a submission checklist. Pursue, or stop at "public GitHub + hahnsolo-hosted demo"?
- **OQ4 — Manual entitlement seeding format for PRD-000.** Two options: (a) operator hand-runs SQL `INSERT INTO tenants ...` against Supabase; (b) repo ships a `seed-entitlements.json` file the adapter reads at startup. Pick at /create-prd or architecture stage.
- **OQ5 — Tenant-id durability + user-identity stability** (real-tenant probe before PRD-001). Pause / detour to SDK Sandbox if probing reveals durability issues.
- **OQ6 — Merchant-of-record / Marketplace ToS legal review** (pre-PRD-001 operator homework). Confirms Lemon Squeezy is acceptable; falls back to Stripe + self-merchant if not.
- **OQ7 — Customer-portal iframe embedding** (PRD-003 design). Lemon Squeezy's hosted customer portal opens in a new tab by default (third-party cookie + iframe-sandbox issues). Can it be safely iframed inside the Standalone admin view, or is "open in new tab → return → app auto-refreshes entitlement" the right UX?
- **OQ8 — Second extension point for PRD-000?** Decided as **no** (D11 confines PRD-000 to SitecoreAI Full Screen). Open as a follow-on: a Dashboard Widget "Your plan: Pro · 3/5 seats used" tile is a natural showcase for the gate-aware library at small surface size. PRD-002 candidate.
- **OQ9 — Concurrent-seat-grab race condition handling.** Two users open the app at the same time when 1 seat is free → exactly one wins, the other sees "seats full." Naive `INSERT … ON CONFLICT` works for Postgres; needs explicit acceptance test in PRD-002. Note for QA spec.
