## 1. Architecture Overview

**What we're building:** A single Next.js (App Router) application — installed as a **custom Cloud Portal Marketplace app** on the `xmc:fullscreen` extension point — that demonstrates a paywall pattern end-to-end. The app has no real feature behind the gate; the gate pattern *is* the feature. Two clean abstraction boundaries (`EntitlementStore`, `PaymentProvider`) live in `src/lib/paywall/` and are the unit of reuse for adopters who fork the repo.

**At what altitude:** Feature-equivalent of a single iframe-mounted page. Architecture is deliberately small: one Next.js app, one Supabase project, no server-side API routes (ADR-0005), no webhook handler (PRD-001), no monorepo. The "system" is the iframe ↔ portal ↔ Supabase triangle plus the abstraction interfaces that decouple those edges.

**Inherited locked decisions** (not re-decided here):

- 4a client-side iframe scaffold — ADR-0005
- Custom-app registration — ADR-0006
- Single Next.js app + `src/lib/paywall/` codebase shape — PRD § 9
- `EntitlementStore` / `EntitlementSeed` interface split — ADR-0002
- `PaymentProvider` as type-only placeholder — ADR-0003
- Env-flag signaled pass-through, banner copy locked — ADR-0004
- Compile-time dev-override guard — PRD NFR-5
- Top-level React error boundary — PRD NFR-6
- Supabase Postgres schema — PRD § 10
- 5-tranche release plan — PRD § 12

**New architectural commitments this document makes** (candidate ADRs at § 11):

- Context-readiness signal: gate awaits the `MarketplaceProvider` async-init resolution; no polling of `application.context`.
- Skeleton variation strategy: single generic skeleton occupying the gated subtree footprint.
- Supabase setup ergonomics: copy-pasteable SQL migration block in README + `.env.example` (no `supabase init` automation, no `pnpm setup:supabase` wizard).
- RLS posture: RLS **enabled but not relied on** for client-side reads in PRD-000; entitlement reads use anon key against tables exposed to the iframe; service-role key is server-side / CLI only.

## 4. Data Model

The authoritative SQL schema lives in **PRD-000 § 10**. This section supplements (does not duplicate) with index strategy, RLS posture, and query patterns.

### 4.1 Tables (summary — see PRD § 10 for full DDL)

| Table | Purpose | PRD-000 usage |
|-------|---------|---------------|
| `tenants` | Subscription state per tenant | Seeded via CLI |
| `seats` | Per-user seat assignment within a tenant | Seeded via CLI |
| `purchase_events` | Provider event idempotency log | **Empty in PRD-000** — provisioned for PRD-001 webhook |

### 4.2 Indexes (supplement to PRD § 10)

PRD § 10 declares primary keys but not auxiliary indexes. Architecture recommends:

| Index | Rationale | Cost |
|-------|-----------|------|
| `tenants(tenant_id)` — PK, already covered | `getEntitlement` step 1 lookup | Free |
| `seats(tenant_id, user_id)` — composite PK, already covered | `getEntitlement` step 2 lookup AND step 3 count by tenant | Free |
| **(deferred)** `seats(tenant_id)` standalone index | If COUNT(*) on the composite PK shows scan inefficiency in production volumes | Defer until measurable |
| `purchase_events(provider_event_id)` — UNIQUE, already covered | PRD-001 webhook idempotency | Free |

No additional indexes added in PRD-000. The composite PK on `seats` covers both the point-lookup (step 2) and the prefix scan for COUNT (step 3) cleanly at PRD-000–002 volumes per assumption A5.

### 4.3 RLS posture (new architectural decision — candidate ADR)

**Decision:** Enable Row Level Security on all three tables but **do not rely on it as the authorization boundary in PRD-000**. PRD-000 uses:

- **Anonymous Supabase key** for client-side reads from the iframe (the `getEntitlement` path).
- **Service-role key** server-side / CLI only (state-switcher; PRD-001's webhook handler).

**Why enable RLS but not rely on it in PRD-000:**

- Adopters who copy `src/lib/paywall/` into production-grade apps need RLS turned on by default — Supabase free-tier projects with RLS disabled are a documented foot-gun.
- PRD-000's threat model is narrow: the operator is the only entity writing tables (via CLI). Reads from the iframe are scoped to the operator's own tenant.
- A future ADR in PRD-002 or post-PRD-003 will revisit RLS policies once multiple real tenants share the same Supabase project (the SaaS-style deployment scenario). PRD-000 leaves a documented placeholder policy (`USING (true)`) and a TODO in `supabase/schema.sql` explaining the deferral.

**Schema migration block (supabase/schema.sql)** includes:

```sql
-- PRD-000 RLS posture: enabled, permissive default policy.
-- Production adopters MUST replace these policies with tenant-scoped predicates.
ALTER TABLE tenants ENABLE ROW LEVEL SECURITY;
ALTER TABLE seats ENABLE ROW LEVEL SECURITY;
ALTER TABLE purchase_events ENABLE ROW LEVEL SECURITY;

CREATE POLICY "anon read tenants (PRD-000 placeholder)" ON tenants FOR SELECT USING (true);
CREATE POLICY "anon read seats (PRD-000 placeholder)" ON seats FOR SELECT USING (true);
-- purchase_events: no anon read policy. Service-role only.
```

This is the **OQ-Arch-5 resolution** — copy-pasteable SQL block in `supabase/schema.sql`, not a `supabase init` automation, not a wizard. Lowest-friction quickstart that still surfaces the RLS knob explicitly.

### 4.4 Entitlement evaluation algorithm

PRD § 10 specifies pseudocode. The architectural commitment is:

- **Three sequential Supabase calls** (`tenant select` → `seat select` → `seat count`). No transaction, no stored procedure — Supabase PostgREST doesn't support multi-statement transactions over REST, and the consistency cost of "tenant flipped to cancelled mid-evaluation" is acceptable for a UX-only decision.
- **Concurrent-seat-grab race** (e.g., two users hit step 3 simultaneously when 1 seat is free) — explicitly deferred to PRD-002 (per PRD § 14 OQ-PRD002-1). PRD-000's CLI-seeded model means there are no concurrent grabs.

### 5.5 Supabase API contract (used by `SupabaseStore`)

Uses `@supabase/supabase-js`. Three calls per `getEntitlement`:

```typescript
// src/lib/paywall/stores/SupabaseStore.ts (architectural shape)
import { createClient, SupabaseClient } from '@supabase/supabase-js';

export class SupabaseStore implements EntitlementStore, EntitlementSeed {
  constructor(private readonly db: SupabaseClient) {}

  async getEntitlement(tenantId: string, userId: string): Promise<EntitlementResult> {
    // 1. Tenant select
    const { data: tenant } = await this.db
      .from('tenants').select('status, seats_total')
      .eq('tenant_id', tenantId).maybeSingle();
    if (!tenant || tenant.status !== 'active') return { status: 'tenant_no_subscription' };

    // 2. Seat select
    const { data: seat } = await this.db
      .from('seats').select('user_id')
      .eq('tenant_id', tenantId).eq('user_id', userId).maybeSingle();
    if (seat) return { status: 'allowed' };

    // 3. Seat count
    const { count } = await this.db
      .from('seats').select('user_id', { count: 'exact', head: true })
      .eq('tenant_id', tenantId);
    if ((count ?? 0) >= tenant.seats_total) {
      return { status: 'tenant_active_seats_full', seatsTotal: tenant.seats_total };
    }
    return { status: 'tenant_active_user_unassigned' };
  }
  // seedTenant, seedSeat, clearState — implement EntitlementSeed
}
```

Errors (network, RLS rejection, malformed rows) propagate as thrown promise rejections to the gate's error path → top-level `<ErrorBoundary>` (NFR-6).

## 8. Security Considerations

### 8.1 Environment-variable classification (NFR-5)

| Variable | Classification | Enforcement |
|----------|---------------|-------------|
| `NEXT_PUBLIC_PAYWALL_ENABLED` | **Non-sensitive public** | Visible in client bundle. Boolean signal only; no auth bypass. |
| `NEXT_PUBLIC_SUPABASE_URL` | **Public (intentional)** | Supabase URLs are non-sensitive. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | **Public (intentional, RLS-gated)** | Anon key is meant to be in the client bundle. RLS policies are the boundary. |
| `SUPABASE_SERVICE_ROLE_KEY` | **SECRET — server/CLI only** | NOT prefixed `NEXT_PUBLIC_`. Next.js tree-shakes from client bundle. |
| `PAYWALL_DEV_OVERRIDE_USER_ID` | **SECRET — server-only** | NOT prefixed `NEXT_PUBLIC_`. Compile-time guard adds dead-code-elimination layer. |
| `OPERATOR_TENANT_ID` / `OPERATOR_USER_ID` | **Local dev only** | `.env.local` (gitignored). Never deployed. |

### 8.2 Compile-time dev-override guard (NFR-5)

**Implementation contract** (locked at architecture level — Lead Developer implements exactly):

```typescript
// src/lib/paywall/PaywallGate.tsx — Step 4 in FR-1 sequence
if (
  process.env.NODE_ENV !== 'production' &&
  process.env.PAYWALL_DEV_OVERRIDE_USER_ID &&
  context.user?.id === process.env.PAYWALL_DEV_OVERRIDE_USER_ID
) {
  // short-circuit to allowed
}
```

**Why both conditions matter:**

- `process.env.NODE_ENV !== 'production'` — Next.js statically replaces `process.env.NODE_ENV` at build time. When `NODE_ENV === 'production'`, this expression collapses to `false` and Webpack tree-shaking removes the entire `if` branch (including the env-var read). Result: the override code path doesn't exist in production bundles.
- The env-var read inside the branch — only reached when `NODE_ENV !== 'production'`. In dev, this resolves on the server (Next.js doesn't inline non-`NEXT_PUBLIC_` env vars to the client) — but in PRD-000's 4a scaffold, gate code runs client-side. **This means the dev override is effective only when the dev server sees the env var at build time** (e.g., via `.env.local`).

**Verification gate at Tranche D:** `pnpm build` + grep `.next/` output for `PAYWALL_DEV_OVERRIDE_USER_ID` — must NOT appear (per PRD § 12 Tranche D gate).

### 8.3 Supabase RLS posture

See § 4.3. PRD-000 enables RLS with permissive default policies. Production adopters MUST harden policies. README and `supabase/schema.sql` flag this explicitly.

### 8.4 No secrets in client bundle

- Service-role key: never `NEXT_PUBLIC_*`.
- Dev override: never `NEXT_PUBLIC_*` + compile-time guard.
- `.env.local` gitignored.
- README's "Configuration" section explicitly enumerates which env vars ship to the client and which do not.

### 8.5 Error-boundary safety

Per NFR-6:

- `<ErrorBoundary>` is placed at `src/app/layout.tsx` wrapping the entire page tree.
- It logs to `console.error` with prefix `[PaywallBlueprint]` so adopters can grep logs.
- It does NOT log captured exception payloads to a third party in PRD-000 (no Sentry integration). Adopters add their own.
- **Free section must render even when gated subtree throws** — the boundary is positioned so that `<FreeSection />` is a sibling of the gate's subtree, not a child of it. Architecture commits to a layout shape where the boundary scope is the gated section only (NOT the whole page) OR the page composes free + gated with the boundary wrapping just the gated half. The simpler implementation: render `<FreeSection />` outside the `<ErrorBoundary>`, render `<GatedSection>` inside. Lead Developer enforces this layout in `src/app/page.tsx`.

### 8.6 Iframe sandbox + postMessage origin

Per `marketplace-sdk-client` § 8c: XM Cloud may set `sandbox` attributes on the iframe. PRD-000 doesn't use WebGL or sandbox-restricted APIs; no architectural concern. The Marketplace SDK's `target: window.parent` + auto-detected origin handles the postMessage boundary cleanly.

## 9. Risks & Tradeoffs

### 9.1 Inherited from PRD § 13 (no re-statement; pointers only)

- **R1** — `application.context` shape assumptions wrong. Mitigated by OA-1 probe (Tranche B) + defensive layered render (FR-9).
- **R2** — Marketplace ToS / merchant-of-record. Not architectural concern in PRD-000.
- **R3** — Freemium scope creep. Mitigated by minimal `<FreeSection />` (one paragraph + one mock UI).
- **R4** — Out-of-band webhook decision deferred to PRD-001. ADR-0005.
- **R5** — OSS expectations escalate. Not architectural.
- **R6** — Iframe mount lifecycle race. **See § 9.2 — newly resolved with architectural commitment.**
- **R7** — Banner visual interference. UI design concern.
- **R8** — DQ4 scaffold-choice consequence (PRD-001 migration cost). ADR-0005.

### 9.2 New architectural risks

**AR-1 — Context-readiness signal mechanism not declaratively documented by SDK** (resolves R6).

**Risk:** The Marketplace SDK Client skill (§ 2) documents the `MarketplaceProvider` pattern but does not name a single explicit "context-ready" event. The provider renders children only after `ClientSDK.init()` resolves AND `client.query('application.context')` resolves. If a future SDK version changes the provider's resolution semantics, the gate's assumption ("by the time my children render, `applicationContext` is non-null") could break silently.

**Mitigation (architectural decision):**

- Gate code MUST consume `applicationContext` via `useAppContext()` from the scaffold's provider, not via direct `client.query` calls. The provider IS the readiness signal.
- Gate's FR-1 step 2 ("wait for context-ready") in practice means: if `useAppContext()` returns `null`/`undefined`, render the skeleton. The provider's contract is that children only render after init — but defensively, the gate handles `null` anyway.
- A Vitest unit test asserts that a `useAppContext()` returning `null` produces a skeleton, not a thrown error. This guards against silent regression if the provider semantics change.

**AR-2 — Single-skeleton vs four-skeleton layout-shift risk** (resolves OQ-Arch-6).

**Decision:** **One generic `SkeletonState.tsx`** sized to the largest of the four resolved states. Rationale: pre-resolution the gate doesn't know which state it will land on, so per-state skeletons would require speculative rendering (pick the wrong skeleton → layout shift when the real state replaces it). A single skeleton sized to the largest resolved-state footprint absorbs layout shift uniformly. UI Designer specifies the skeleton dimensions in the next stage; architecture commits to the one-skeleton approach.

**AR-3 — Supabase free-tier connection limits at OSS-adopter scale.**

**Risk:** If many adopters fork and point at the same demonstration Supabase project (unlikely but possible — README explicitly tells adopters to stand up their own), connection pool exhaustion could cause flaky entitlement reads.

**Mitigation:** README "Configuration" section says explicitly: "Adopters MUST stand up their own Supabase project. Do not point your fork at the blueprint's demo Supabase URL." Architecture has no further protection — this is policy, not code.

### 9.3 Tradeoffs explicitly accepted

| Tradeoff | Chosen | What we give up |
|----------|--------|-----------------|
| 4a client-side vs 4b full-stack | 4a (ADR-0005) | Cannot add Next.js API route for PRD-001 webhook; uses out-of-band hosting instead. Documented as a feature. |
| Anon-key reads from iframe vs server-mediated reads | Anon-key direct | Less attack-surface isolation; relies on RLS as the boundary in production. PRD-000 ships permissive policies — adopters harden. |
| Single skeleton vs four | Single (AR-2) | Skeleton footprint slightly larger than three of the four states. Acceptable. |
| One-shot entitlement fetch vs live subscription | One-shot | Entitlement changes mid-session not reflected until reload. PRD-002+ revisits if seat-management UX needs liveness. |
| Static schema migration block vs `supabase init` automation | Static SQL block in `supabase/schema.sql` (OQ-Arch-5) | Adopters who use `supabase` CLI miss the automation. Trade: README has fewer moving parts; clearer to a cold-reader. |

## 11. Key decisions (for ADRs)

Decisions in this run that are NOT already in ADR-0001 through ADR-0006 and warrant their own ADR. Aim of ≤4 to avoid the 5+ HARD STOP gate.

1. **ADR-0007 — Single generic skeleton sized to largest resolved state.** The gated subtree renders one `SkeletonState.tsx` sized to absorb the largest of the four resolved states (likely `tenant_active_seats_full` per its two-CTA layout). Alternatives considered: four per-state skeletons (rejected — pre-resolution the gate cannot know which to render → layout shift), no skeleton (rejected — flash-of-allowed risk per DQ3). Consequence: skeleton footprint is slightly oversized for three of the four states; layout-shift risk is uniformly eliminated.

2. **ADR-0008 — Context-readiness signal sourced from `MarketplaceProvider` resolution, not from a dedicated SDK ready-event.** Gate code consumes `applicationContext` via the scaffold's `useAppContext()` hook; the provider's contract that it renders children only after `ClientSDK.init()` AND `client.query('application.context')` resolve IS the readiness signal. The gate additionally treats a `null`/`undefined` context defensively (renders skeleton) to guard against future provider-semantic changes. Alternative considered: poll `application.context` from the gate directly (rejected — duplicates the provider's work, risks race conditions).

3. **ADR-0009 — Supabase RLS enabled with permissive default policies for PRD-000; production adopters harden.** `supabase/schema.sql` enables RLS on all three tables and ships placeholder `USING (true)` policies for anon read on `tenants` and `seats`. `purchase_events` has no anon policy (service-role only). README flags this explicitly as adopter-action-required. Alternative considered: ship full tenant-scoped policies (rejected — PRD-000 has one tenant, one operator; tenant-scoping requires JWT-based identity propagation from the iframe to PostgREST that isn't wired yet; revisit in PRD-002 when multi-tenant becomes real).

4. **ADR-0010 — Supabase setup via copy-pasteable SQL migration block in `supabase/schema.sql`, not via `supabase init` automation or a `pnpm setup:supabase` wizard.** Resolves OQ-Arch-5. README's Quickstart instructs adopters: (1) create Supabase project in dashboard, (2) capture URL + keys, (3) copy `supabase/schema.sql` into the SQL editor, (4) paste env vars into `.env.local`. Alternative considered: `pnpm setup:supabase` wizard (rejected — adds CLI dep + automation surface; cold-reader (G3) friction outweighs DX gain at PRD-000 scale).

**Decisions explicitly NOT added as new ADRs** (already covered or too small):

- Error-boundary placement (`src/app/layout.tsx` wrapping the gated subtree, free section outside scope) — covered by NFR-6 + § 8.5; no separate ADR.
- Single-skeleton implementation detail — folded into ADR-0007 above.
- `<PaywallGate>` injectable `store` prop with module-level default — implementation detail; covered by § 5.1.
