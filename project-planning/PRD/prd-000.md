## 1. Executive Summary

**Paywall Blueprint** is a public OSS reference Sitecore Marketplace App that demonstrates how to integrate a paywall — tenant entitlement check, per-user seat enforcement, self-service purchase, license sync — into a Marketplace App end-to-end. It is the **first publicly available worked example** of monetizing a Sitecore Marketplace App. The reference app itself has no real feature behind the paywall; the paywall flow IS the feature. The deliverable is an installable Cloud Portal Marketplace App on the **SitecoreAI Full Screen** extension point that demonstrates a freemium pattern (free piece + gated premium piece on one page) plus four denial-state UX screens, all driven by a `<PaywallGate>` React wrapper and an entitlement store. Two clean abstraction boundaries — a `PaymentProvider` adapter (Lemon Squeezy in v1, swappable) and an `EntitlementStore` adapter (Supabase Postgres in v1, swappable) — let adopters fork the repo, replace placeholder concerns, and ship a monetized Marketplace App without reinventing the gating pattern.

PRD-000 delivers the **foundation tranche** of a four-PRD product. It establishes the gate component, the entitlement-store abstraction, the four denial UX states (with manually-seeded entitlements — no real provider yet), the env-flag toggle that switches the gate between enforced and demo modes, and the OSS launch surface (public GitHub repo + README). PRD-001 adds the real Lemon Squeezy provider + webhook handler. PRD-002 adds seat-management UI. PRD-003 adds the self-service customer portal. The blueprint is architected as public-app-ready from day one (Blok compliance, accessibility) but registered as a **custom app** for PRD-000 ship; submission to the public Sitecore Marketplace listing is deferred to a post-PRD-003 stretch.

## 2. Problem Statement

Sitecore's Cloud Portal Marketplace today provides **no built-in commerce primitives**. Every team that wants to charge for a Marketplace App — whether freemium or fully paid — starts from zero on every decision: which payment provider, how to map Cloud Portal tenants to subscription objects, how to enforce seats inside an iframe sandbox, what to show editors when access is denied, how to handle reinstalls, how to wire webhooks back to entitlements, what to do when the payments provider is down. The result is that the Marketplace ecosystem stays effectively **free-only** because the per-app cost of inventing a paywall in isolation is too high.

A vendor-neutral, opinionated, public worked example removes that barrier. With a forkable reference repo and a documented swap-point pattern, adopters move from "I'd have to invent a paywall from scratch" to "I fork this repo and replace one component." This unlocks the first wave of paid / freemium Marketplace Apps that aren't viable today.

- App-architecture: **client-side iframe (4a)** — no server-side API routes in PRD-000.
- App registration: **custom app** in Cloud Portal (Sitecore review not required for custom; public-Marketplace submission deferred to post-PRD-003).

  - `allowed` → renders children
  - `tenant_no_subscription` → "Start subscription" denial screen with placeholder CTA URL
  - `tenant_active_seats_full` → "Seats full" denial screen with upgrade CTA
  - `tenant_active_user_unassigned` → "No access yet" screen

- **Defensive layered render** for post-gate welcome (gracefully falls back when `application.context` fields are missing).

- **Reference app single-page layout** with two visually distinct sections:
  - Top section: **free content** — minimal one-paragraph + one mock UI element. Renders for every viewer regardless of entitlement.
  - Bottom section: **gated content** — wrapped by `<PaywallGate>`. Post-gate welcome reads `application.context` for grounded "Welcome [user] for [tenant]" display.
- **Env-flag toggle** `NEXT_PUBLIC_PAYWALL_ENABLED`:
  - When `true` (enforced mode): gate evaluates entitlement; renders one of four UX states.
  - When `false` (demo mode): gate renders children verbatim PLUS a persistent "Paywall disabled — demo mode" banner.
- **Dev override** `PAYWALL_DEV_OVERRIDE_USER_ID` env var — short-circuits the gate to `allowed` when the SDK-resolved user id matches.
- **Blok compliance from day one** — Blok tokens for colors, spacing, typography; WCAG AA accessibility.
- **OSS launch artifact:**
  - Public GitHub repo at `https://github.com/Chris1415/Sitecore.Plugin.PaywallBlueprint` (private during development; flipped to public visibility at ship moment).
  - README documenting the pattern, the two adapter interfaces, the env-flag, the swap-points, and an adoption guide (primary path = fork; secondary path = copy `src/lib/paywall/`).
  - CHANGELOG entry for PRD-000.
  - `docs/cold-read-notes.md` recording G3 cold-reader outcome.

## 6. User Stories

### US-1 — Allowed user sees premium content

**As an** editor on a tenant with an active subscription and an assigned seat,
**when I** open the Paywall Blueprint app from Cloud Portal,
**I want** to see the premium content with my name and my tenant's name displayed,
**so that** I have confirmation that the gate recognized me and granted access.

**Acceptance criteria:**

- The free section at the top of the page renders within 1 second of app mount.
- The gated section initially renders a skeleton placeholder for up to 2 seconds while entitlement is fetched.
- Once the entitlement resolves to `allowed`, the skeleton is replaced with the post-gate welcome screen.
- The welcome screen renders user + tenant identity per the defensive layered render priority chain defined in FR-9 (single source of truth — AC does not re-spec the chain to avoid divergence).
- No banner is shown when `NEXT_PUBLIC_PAYWALL_ENABLED=true`.

### US-2 — Tenant has no subscription

**As an** editor on a tenant that does not have an active subscription,
**when I** open the Paywall Blueprint app,
**I want** to see a clear denial screen explaining the situation and offering a next step,
**so that** I know how to get access (or who to ask).

**Acceptance criteria:**

- The gated section resolves to the `tenant_no_subscription` UX state within 2 seconds of mount.
- The state shows a heading conveying "Start subscription" intent (final copy from UI designer).
- The state shows a primary CTA labeled per the copy quality bar (warm, no shame, clear next step) that links to the provider's checkout URL. In PRD-000 this is a placeholder URL (e.g., `https://example.com/buy`); PRD-001 replaces it with a real Lemon Squeezy URL.
- The free section above continues to render normally and is visible above the denial screen on the same page.

### US-3 — Tenant subscribed, user has no seat

**As an** editor on a tenant with an active subscription but I have not been assigned a seat,
**when I** open the Paywall Blueprint app,
**I want** to see a screen explaining that my tenant admin has not given me access,
**so that** I know to contact my admin rather than think the app is broken.

**Acceptance criteria:**

- The gated section resolves to the `tenant_active_user_unassigned` UX state within 2 seconds of mount.
- The state shows a heading conveying "No access yet" intent.
- The state names the admin role conceptually (e.g., "Ask your team admin") without exposing specific admin user IDs.
- No "Request seat" CTA in PRD-000 (deliberate — disabled-button UI signals broken pattern to adopters). The "Request seat" action lands in PRD-002 alongside the notification flow.
- The free section above continues to render normally.

### US-4 — Tenant at seat capacity

**As an** editor on a tenant whose subscription has all seats taken and I am not one of the assigned seats,
**when I** open the Paywall Blueprint app,
**I want** to see a screen explaining the seat capacity is full and offering an upgrade path,
**so that** I or my admin can take action.

**Acceptance criteria:**

- The gated section resolves to the `tenant_active_seats_full` UX state within 2 seconds of mount.
- The state shows the current seat usage in human-readable form (e.g., "5 of 5 seats in use" — exact copy from UI designer).
- The state offers two CTAs: a primary "Upgrade plan" CTA (placeholder URL in PRD-000) and a secondary message about admin reassignment.
- The free section above continues to render normally.

### US-5 — Free section visible regardless of entitlement state

**As any** editor (paid or unpaid, with seat or without),
**when I** open the Paywall Blueprint app,
**I want** to see the free section content at the top of the page immediately,
**so that** I always get *some* value from the app and the freemium-within-app pattern is visible to me.

**Acceptance criteria:**

- The free section renders within 1 second of app mount regardless of entitlement-store fetch state.
- The free section does not depend on `application.context` resolution (it renders with anonymous content suitable for any viewer).
- The free section is visually distinct from the gated section (clear separator, distinct heading hierarchy).
- The free section content is intentionally minimal: one paragraph of explanatory text + one mock UI element (e.g., a tile or button) demonstrating "this is where free features go."

### US-6 — Adopter disables paywall via env-flag

**As an** adopter of the blueprint working locally on a fork (or running a self-hosted "everything-free" deployment),
**when I** set `NEXT_PUBLIC_PAYWALL_ENABLED=false`,
**I want** the gate to render the gated content verbatim and visibly signal that the paywall is disabled,
**so that** I can iterate on the gated content without entitlement-store roundtrips and so that the OSS-fork story is honest about which mode is active.

**Acceptance criteria:**

- When `NEXT_PUBLIC_PAYWALL_ENABLED=false`, the `<PaywallGate>` renders children verbatim with no entitlement-store call.
- A persistent banner labeled "Paywall disabled — demo mode" is visible on the page when the flag is off. Banner styling decisions land at `/architect`.
- Toggling the flag at compile time (re-deploy) visibly removes / adds the banner and changes gate behavior.
- The dev override `PAYWALL_DEV_OVERRIDE_USER_ID` has no effect when `NEXT_PUBLIC_PAYWALL_ENABLED=false` (the flag takes precedence — flag-off bypasses the gate entirely).

### US-7 — Local developer bypasses gate via dev override

**As a** local developer running the reference app or an adopter fork on `localhost`,
**when I** set `PAYWALL_DEV_OVERRIDE_USER_ID=<my-user-id>`,
**I want** the gate to short-circuit to `allowed` when the SDK-resolved user id matches my override value,
**so that** I can iterate on the gated content without manually seeding entitlements.

**Acceptance criteria:**

- When `PAYWALL_DEV_OVERRIDE_USER_ID` is set AND `NEXT_PUBLIC_PAYWALL_ENABLED=true`, the gate skips the entitlement-store call IF the SDK-resolved user id matches.
- When the override does not match the SDK user id (e.g., a different teammate is testing), the gate runs the entitlement-store check normally.
- The dev override is documented in the README under a "Local development" section.
- The dev override is intentionally an environment variable (not a UI toggle) to keep it explicit and out of production state.

## 7. Functional Requirements

### FR-1 — `<PaywallGate>` component contract

The library MUST export a `<PaywallGate>` React component (functional, hooks-based) with the following contract:

- **Props:** `children` (ReactNode); optional `onStateChange` callback receiving the resolved entitlement state.
- **Behavior on mount:**
  1. Read `NEXT_PUBLIC_PAYWALL_ENABLED`. If `false`, render `children` + the demo-mode banner (rendered via a sibling component or portal — banner placement is a UI concern).
  2. **Wait for the Marketplace SDK provider's `context-ready` signal.** Render the skeleton in the gated subtree position until both context is ready AND the entitlement promise resolves. (The exact ready-signal mechanism — promise resolution, hook state flag, or `application.context` non-null — is locked in `/architect` after the DQ6 probe captures actual SDK behavior. This step replaces the earlier "synchronous read" framing to align with R6 mitigation.)
  3. Once context is ready, read `application.context`. Validate that `tenantId` and `userId` are non-empty strings; if either is missing/malformed, fall through to the top-level React error boundary (see NFR-6).
  4. Read `PAYWALL_DEV_OVERRIDE_USER_ID`. If set AND matches `context.user.id`, short-circuit to `allowed` without calling the entitlement store.
  5. Otherwise call `EntitlementStore.getEntitlement(tenantId, userId)`. While the promise is pending, continue rendering the skeleton.
  6. On resolution, render the matching UX state (one of the four discriminated-union variants in FR-2).
- **Error handling:** If the entitlement-store call rejects OR `application.context` is malformed, the component throws — the surrounding top-level error boundary (NFR-6) renders a generic "Something went wrong — please try again" message. PRD-000 deliberately does not implement an in-gate retry UX; PRD-001 will introduce explicit provider-unreachable UX with retry logic.

### FR-2 — `EntitlementStore` interface contract (split: runtime vs seed)

The library MUST export **two separate TypeScript interfaces** to avoid contract pollution. Adopters who swap the store in production only need to implement the runtime interface.

**`EntitlementStore` (production-runtime contract — required for adopters):**

- `getEntitlement(tenantId: string, userId: string): Promise<EntitlementResult>`

**`EntitlementSeed` (dev / CLI contract — optional for adopters; required for the state-switcher CLI):**

- `seedTenant(args: { tenantId: string, plan: string, seatsTotal: number, status: 'active' | 'cancelled' | 'past_due' }): Promise<void>`
- `seedSeat(args: { tenantId: string, userId: string }): Promise<void>`
- `clearState(): Promise<void>`

The blueprint's `SupabaseStore` class MUST implement both interfaces. Adopters who fork and swap stores only need their replacement class to implement `EntitlementStore`; the seed interface can be skipped entirely (their dev / smoke flow may differ).

**`EntitlementResult` is a discriminated union with exactly four variants** (no fifth "error" variant — errors propagate via promise rejection to the FR-1 error boundary):

```typescript
type EntitlementResult =
  | { status: 'allowed' }
  | { status: 'tenant_no_subscription' }
  | { status: 'tenant_active_seats_full'; seatsTotal: number }
  | { status: 'tenant_active_user_unassigned' };
```

**Note on `seatNumber` (removed from PRD-000):** The earlier draft included `seatNumber` on the `allowed` variant. It served no PRD-000 user story (FR-9 doesn't use it) and the seat-numbering algorithm is undefined. Removed for PRD-000; if PRD-002's seat-management UI needs ordinal seat numbers, the interface extends then.

PRD-001 will extend `EntitlementStore` with `recordPurchaseEvent` for webhook idempotency.

### FR-3 — `SupabaseStore` adapter implementation

The library MUST provide a concrete `SupabaseStore` class implementing **both** the `EntitlementStore` and `EntitlementSeed` interfaces against a Supabase Postgres database.

**Schema:** The authoritative schema definition lives in § 10 Data Model Overview (single source of truth). The `SupabaseStore` queries MUST match that schema exactly. Earlier divergence between FR-3 and § 10 (`last_seen_at`, `created_at`, `updated_at`) is resolved by deferring to § 10.

### FR-4 — Reference app single-page freemium layout

The reference Marketplace App MUST render a single page (no client-side routing) with two visually distinct sections:

- **Top section (free):** A minimal informational area — one paragraph of copy + one mock UI element. No SDK reads. Always visible. Marked clearly as "free" or equivalent.
- **Bottom section (gated):** Wrapped by `<PaywallGate>`. Contains the post-gate welcome screen (allowed state) or one of three denial screens. Marked clearly as "premium" or equivalent.

Both sections MUST be visible on a single screen without scrolling on a standard SitecoreAI Full Screen viewport (≥ 1024×768 effective viewport inside the iframe).

### FR-5 — Four UX states UI

Each of the four denial states (allowed, no-sub, seats-full, unassigned) MUST be rendered by a distinct, identifiable component. Each component MUST:

- Use Blok-compliant tokens for colors, spacing, and typography.
- Meet WCAG AA contrast ratios.
- Be keyboard-navigable (focus order, visible focus rings).
- Render copy that satisfies the quality bar set in § 11.

### FR-6 — Env-flag toggle + demo-mode banner

The library MUST honor `NEXT_PUBLIC_PAYWALL_ENABLED`:

- `=true` (or unset — default is enforced): gate evaluates normally.
- `=false`: gate is a fragment pass-through; a persistent banner displays the "Paywall disabled — demo mode" message.

The banner MUST be visible on the page when the flag is off and absent when it is on. Banner placement, exact wording (within the quality bar), and styling are UI design concerns (`/architect`).

### FR-7 — Dev override env var

The library MUST honor `PAYWALL_DEV_OVERRIDE_USER_ID`. When set AND the SDK-resolved `context.user.id` matches the override value AND `NEXT_PUBLIC_PAYWALL_ENABLED=true` AND `NODE_ENV !== 'production'` (compile-time check per NFR-5), the gate short-circuits to `allowed` without calling the entitlement store.

The override MUST be intentionally narrow: only matching the named user id, not "anyone on localhost." This keeps the override explicit and prevents accidental disclosure in shared dev environments. The compile-time `NODE_ENV` guard ensures the override branch is dead-code-eliminated from production bundles.

### FR-8 — State-switcher CLI

The repo MUST ship a CLI command (`pnpm seed:state <state>`) that flips the Supabase entitlement state to one of: `allowed`, `no-sub`, `seats-full`, `unassigned`. **CLI is the committed approach** — no JSON-seed alternative. Rationale: the smoke walkthrough needs to flip states quickly across screenshots, and one command per state is cleaner in the README than "edit this JSON then restart." Operator chose CLI in /create-prd DQ1 with the JSON option held as alternative; the alternative is now closed.

The CLI MUST:

- Read tenant/user identifiers from a local `.env.local` (operator's tenant + operator's user id, captured during the DQ6 probe).
- Implement against the `EntitlementSeed` interface (so the same CLI works against any seed-capable adapter).
- Idempotently apply the target state (truncate + reseed, OR upsert — implementation detail in `/architect`).
- Print a clear success message naming the state applied (e.g., "✓ State applied: seats-full (tenant=foo, seats_total=5, current_seats=5)").

### FR-9 — Post-gate context-grounded welcome

When the gate resolves to `allowed`, the rendered post-gate component MUST display the user's identity and tenant's identity, sourced from `application.context`. The component MUST implement defensive layered rendering:

- Display priority (user): `context.user.name` → `context.user.email` → `"there"` (generic fallback).
- Display priority (tenant): `context.tenant.name` → truncated `context.tenant.id` (last 8 chars) → `"your tenant"` (generic fallback).

The exact field names depend on the captured `application.context` shape from the DQ6 probe — final field accessors are confirmed during `/architect`.

## 8. Non-Functional Requirements

### NFR-1 — Performance

- **Gate evaluation latency:** From mount to resolved state, gate MUST complete within 2 seconds on a tenant in the same region as the Supabase instance. The free section MUST render within 1 second regardless of entitlement-store fetch progress.
- **Skeleton display threshold:** If entitlement resolution takes longer than 100ms, the skeleton MUST be visible (no flash of empty content).
- **First contentful paint:** ≤ 2 seconds on the SitecoreAI Full Screen extension point, cold mount.

### NFR-2 — Accessibility

- **WCAG AA compliance** across all four UX states and the free section.
- All interactive elements (CTAs, buttons) keyboard-navigable with visible focus rings.
- All non-text content (mock UI elements, icons) have appropriate text alternatives.
- Color contrast verified against Blok tokens at runtime.

### NFR-3 — Browser support

- Targets the browsers supported by Sitecore Cloud Portal (the parent iframe environment): current Chromium-based browsers (Chrome, Edge), current Firefox, current Safari.
- No support for IE11 or other legacy browsers.

### NFR-4 — Internationalization

- **English only** for PRD-000. i18n support is deferred — all copy lives in untranslated literals.
- The code structure MUST not actively *prevent* future i18n (e.g., copy lives in a single module that could later be wrapped by a translator).

### NFR-5 — Security

- No secrets in client-side bundle. `NEXT_PUBLIC_*` env vars are limited to the env-flag (which is non-sensitive). `PAYWALL_DEV_OVERRIDE_USER_ID` is **NOT** prefixed `NEXT_PUBLIC_` — it is server-side only and Next.js tree-shakes it out of client bundles in production builds.
- The dev override MUST be guarded at compile time, not runtime: the gate's override-check expression MUST be wrapped in `if (process.env.NODE_ENV !== 'production' && process.env.PAYWALL_DEV_OVERRIDE_USER_ID)` so that production builds dead-code-eliminate the entire branch via Next.js / Webpack tree-shaking. Runtime-only guards are insufficient — a misconfigured production build with `NODE_ENV` unset would still leak the override.
- Supabase service-role keys MUST live server-side only (in CI scripts and the state-switcher CLI). Anonymous keys (with row-level security) are used in any client-side context if applicable.

### NFR-6 — Reliability + error boundary

- The reference app MUST wrap `<PaywallGate>` (and the rest of the gated subtree) in a **top-level React error boundary** that renders a generic "Something went wrong — please try again" fallback. The error boundary MUST log the thrown error to `console.error` with a stable prefix (`[PaywallBlueprint]`) so adopters can grep for it in browser DevTools / Vercel logs / Sentry.
- When `<PaywallGate>` encounters a malformed `application.context` (missing `tenantId` or `userId`), it MUST throw — the error boundary catches it and renders the fallback. This is intentional: the gate does not invent UX for "context is broken"; that's a host-page integration error worth surfacing visibly.
- When `EntitlementStore.getEntitlement()` rejects, the rejected promise propagates as a thrown error to the boundary. PRD-000 does not implement in-gate retry; PRD-001 will introduce explicit provider-unreachable UX with retry logic.
- The free section (above the gate) MUST render normally even when the gated subtree falls into the error boundary. Adopters should never see a fully-blank page because of a gate failure.

### NFR-7 — Code quality

- TypeScript strict mode enabled (`strict: true` in tsconfig).
- No `any` types in the public API of the library (`<PaywallGate>`, `EntitlementStore`, adapter implementations).
- Code coverage for the gate logic: ≥ 80% for unit tests on the gate's state-resolution decision tree.

## 10. Data Model Overview

### Supabase Postgres schema (PRD-000 surface)

```sql
CREATE TABLE tenants (
  tenant_id TEXT PRIMARY KEY,
  plan TEXT NOT NULL DEFAULT 'starter',
  seats_total INTEGER NOT NULL DEFAULT 1,
  status TEXT NOT NULL CHECK (status IN ('active', 'cancelled', 'past_due')),
  period_end TIMESTAMPTZ NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE seats (
  tenant_id TEXT NOT NULL REFERENCES tenants(tenant_id) ON DELETE CASCADE,
  user_id TEXT NOT NULL,
  assigned_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_seen_at TIMESTAMPTZ NULL,
  PRIMARY KEY (tenant_id, user_id)
);

CREATE TABLE purchase_events (
  id SERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  provider_event_id TEXT NOT NULL UNIQUE,
  raw_payload JSONB NOT NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**PRD-000 usage:** `tenants` and `seats` populated via state-switcher CLI. `purchase_events` table exists but is empty (provisioned for PRD-001's webhook idempotency).

**Entitlement evaluation logic** (pseudocode, server-side via Supabase SDK):

```typescript
async function getEntitlement(tenantId, userId) {
  const tenant = await supabase.from('tenants').select('*').eq('tenant_id', tenantId).single();
  if (!tenant || tenant.status !== 'active') return { status: 'tenant_no_subscription' };

  const seat = await supabase.from('seats')
    .select('*').eq('tenant_id', tenantId).eq('user_id', userId).single();
  if (seat) return { status: 'allowed', seatNumber: <n>, seatsTotal: tenant.seats_total };

  const seatCount = await supabase.from('seats')
    .select('user_id', { count: 'exact' }).eq('tenant_id', tenantId);
  if (seatCount.count >= tenant.seats_total) {
    return { status: 'tenant_active_seats_full', seatsTotal: tenant.seats_total };
  }
  return { status: 'tenant_active_user_unassigned' };
}
```

### Copy quality bar (DQ5 — final wording from UI designer in `/architect`)

The four denial-state screens and the demo-mode banner inherit the following copy bar:

- **Warm, not punitive.** The denial isn't the editor's fault. Avoid "Access denied" / "You don't have permission" — those phrases shame the user. Prefer framings that suggest action: "Start your subscription," "Ask your admin," "Upgrade for more seats."
- **Clear next-step CTA.** Every denial state has exactly one primary action button with a verb-led label. No "Learn more" placeholders.
- **No scare-quotes around "free."** The freemium pattern is presented neutrally — free tier is a real product surface, not a teaser.
- **Concise.** Headline ≤ 6 words. Body ≤ 2 short sentences.
- **English only** for PRD-000.

The UI designer produces final wording as part of the `/architect` variant proposal. Adopters fork the polished copy as the inherited pattern.

### Skeleton loading state

While the entitlement promise is pending, the gated subtree renders a skeleton placeholder. The skeleton MUST occupy the visual space the resolved state would occupy (no layout shift). Skeleton styling uses Blok loading tokens.

### Demo-mode banner

When `NEXT_PUBLIC_PAYWALL_ENABLED=false`, a banner labeled "Paywall disabled — demo mode" (final copy from UI designer) is persistently visible. Placement, styling, and dismissibility are UI design concerns — but the banner MUST be:

- Visually distinct enough that an observer of a demo video would notice it.
- Not blocking the main content (placed at a page edge — top or bottom recommended).
- Non-dismissible (or dismissibility is session-only) so the signal remains honest.

### Post-gate welcome — defensive layered render

The post-gate welcome screen displays user + tenant identity using the priority chain in FR-9. The screen MUST always render *something* meaningful, even when display fields are absent — the gate's job is to confirm "you have access," and that confirmation cannot fall back to "Welcome `null`!"

## 13. Risks and Mitigations

### R1 — `application.context` shape assumptions wrong (carried from brain-dump A1, A2)

**Risk:** If `application.context.tenantId` is not durable across reinstalls, or if user identity is not stable / not exposed in a useful form, the entitlement model breaks or the post-gate welcome degrades.

**Mitigation:** DQ6 probe runs in Tranche B before any gate-relevant logic is wired. Captured shape lands in `project-planning/architecture/sdk-fixtures/`. Code uses defensive layered render (FR-9) regardless — the gate always renders something sensible. If the probe reveals a hard structural issue, escalate to operator and consider SDK Sandbox detour (per session intent).

### R2 — Marketplace ToS prohibits external merchant-of-record (carried from A3)

**Risk:** If Sitecore's Marketplace ToS prohibits using a third-party merchant-of-record provider like Lemon Squeezy, PRD-001 must pivot to Stripe + self-merchant (and self-handle tax/VAT).

**Mitigation:** Operator legal review pre-PRD-001. The `PaymentProvider` abstraction means swapping to Stripe is one new adapter file. PRD-000 is unaffected — it has no real provider.

### R3 — PRD-000 scope creep from freemium pattern (carried from brain-dump R4)

**Risk:** Adding the freemium-within-app demo (D9) expanded PRD-000 scope. Could overrun the 1–2 day tranche-A-through-D estimate.

**Mitigation:** Keep the free section deliberately minimal (FR-4: one paragraph + one mock UI element). Resist adding any business logic to it during Tranche A. UI designer respects the "free section is minimal" constraint when producing the variant.

### R4 — Out-of-band webhook hosting decision deferred to PRD-001

**Risk:** Choice between Supabase Edge Function vs separate Vercel project for PRD-001's webhook handler isn't made yet. If the operator later finds neither works (auth issues, cold-start latency, signature-verification ergonomics), PRD-001 stalls.

**Mitigation:** PRD-001 architecture stage produces an ADR comparing both options on operational characteristics before committing. PRD-000 is unaffected — it has no webhook handler.

### R5 — Public OSS expectations escalate before v1 stabilizes

**Risk:** Once the repo is public (Tranche E), community may request second-provider adapter (Stripe / Paddle) before Lemon Squeezy is even stable.

**Mitigation:** README explicitly signals "v1 = Lemon Squeezy; second provider after PRD-003 stabilizes." Set an informal issue-triage expectation in CONTRIBUTING.md.

### R6 — Iframe mount lifecycle race condition

**Risk:** If `application.context` is not ready on first render (SDK provider initializes asynchronously), gate behavior at the very first mount could be wrong (e.g., `userId` is undefined → entitlement call fails).

**Mitigation:** Architecture stage documents the SDK provider's context-readiness signal. Gate component waits for the provider to signal "context ready" before calling the entitlement store. Skeleton is shown until both context is ready AND entitlement resolves.

### R7 — Demo-mode banner visual interference with post-gate welcome

**Risk:** A persistent banner on top of a context-grounded "Welcome" screen could look cluttered or interfere with copy.

**Mitigation:** UI designer validates the banner + welcome layout together in the `/architect` variant. Banner placement is a UI concern, not a logic concern.

### R8 — DQ4 scaffold-choice consequence — PRD-001 scaffold migration cost (new)

**Risk:** DQ4's choice of 4a client-side means PRD-001 cannot simply add a Next.js API route — the webhook handler must be hosted out-of-band. If the out-of-band hosting option (Supabase Edge Function or separate Vercel) doesn't work cleanly, PRD-001 incurs a scaffold migration to 4b full-stack.

**Mitigation:** Documented as a *deliberate* trade-off in § 9 ("out-of-band webhook hosting" is part of the abstraction story). PRD-001 architecture stage evaluates the options before committing. Worst case: scaffold migration cost is bounded (~1-day effort) and isolated to PRD-001.
