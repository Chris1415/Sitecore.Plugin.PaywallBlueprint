## 1. Design context & assumptions

### Audience

- **Primary direct consumer of the visual:** Adopters who fork the blueprint. They see this UI and decide whether the pattern is worth inheriting. The visual must feel like "a well-composed Sitecore Marketplace app" — not a hahnsolo-branded product.
- **Secondary consumer:** Sitecore tenant editors / admins who land in the iframe. They see the four UX states. Copy tone and CTA clarity matter more to them than aesthetics.
- **Tertiary consumer:** Demo-video viewer (operator recording the Tranche C / E walkthroughs). The demo-mode banner must read at a glance even in a compressed YouTube frame.

### Goals and success criteria

- Inherit Blok defaults wherever they exist; treat any deviation as a debt to justify.
- Make the freemium pattern legible at a glance: top is free, bottom is gated, the separation is obvious without reading copy.
- Make denial states feel like "next step ahead," not "you're locked out."
- Make the demo-mode banner unmissable to a video viewer **and** non-blocking to the editor doing real work.
- Make the welcome state feel like recognition ("yes, you, on this tenant, here") — never overpromise features the blueprint doesn't have.

### Constraints (brand, a11y, stack)

- **Stack** — Next.js App Router + TypeScript + shadcn/ui + Blok theme (per architecture § 7 + `sitecore:blok-setup`). Tailwind v4 / Nova preset — tokens live in `@theme inline { … }` in `app/globals.css`, not in `tailwind.config.ts`.
- **Theme** — Honor host theme via `application.context`; `bg-background` is the safe default. Never force light/dark — Blok's `.dark` class on `<html>` flips variables automatically.
- **Iframe viewport** — Per `sitecore:blok-marketplace-integration`: 1024–1920px × 600–1080px effective. FR-4 requires both sections visible without scrolling at ≥1024×768. Shadows must stay small (`shadow-sm` / `shadow`) — large shadows clip at iframe edges.
- **Accessibility bar** — WCAG AA per NFR-2. Keyboard-navigable focus order, visible focus rings (Blok `ring-ring` token), runtime contrast verification against Blok tokens.
- **Aesthetic direction (operator-locked)** — Neutral Blok-stock identity. The blueprint reads as "any well-composed Sitecore Marketplace app." Adopters who fork should feel they inherited a clean Blok pattern, not someone else's brand.

### Reference / inspiration

- **Blok primitives catalog** — <https://blok.sitecore.com/primitives> (verified 2026-04-22 per `sitecore:blok-components`).
- **Blok bloks (composites)** — <https://blok.sitecore.com/bloks>.
- **Blok theming tokens** — <https://blok.sitecore.com/theming>.
- **Sister patterns in Sitecore-Marketplace-Apps ecosystem** — Component Usage Atlas, QuickCopy, Page Shot all use `@blok/topbar` + main content area; this spec inherits that shell idiom unchanged. Doing so is the *whole point* of "neutral Blok-stock" — adopters see "oh, this is just what a Marketplace app looks like."

## 2. Design direction

### Visual direction — "Stock Blok"

A deliberately under-designed surface that reads as Sitecore design-system canon. The composition does the talking, not the chrome.

**What this direction IS:**

- Single `@blok/topbar` header with the app name. No tenant switcher, no user menu — the gate handles identity.
- Two `@blok/card` sections stacked vertically with a thin `@blok/separator` between them. The separator is the visible signal: "above = free, below = gated."
- All four denial states share the same card frame, the same icon-headline-body-CTA layout. Differences are purely copy + icon glyph. This sameness IS the design — adopters inherit a *pattern*, not four separate screens.
- Banners (demo mode, error fallback) use `@blok/alert` — Blok's canonical messaging primitive.
- Motion is minimal: 200ms `ease-out` opacity-and-translate-Y(4px) on skeleton-to-resolved transition. No carousels, no slide-ins, no parallax.

**What this direction IS NOT:**

- Not a marketing landing page. No hero image, no testimonial, no CTA grid.
- Not a SaaS dashboard. No data charts, no metric tiles, no sidebar nav.
- Not a paywall product page. No pricing-tier comparison, no FAQ accordion, no badge stack.
- Not opinionated about brand colors. Anything that would read as hahnsolo (specific accent hue, custom typography pairing, brand-specific iconography) is excluded by construction.

**Single viewport budget (≥1024×768 effective per FR-4):**

- Topbar: 56px
- Banner (when present): 52px + 16px gap below
- Free card: ~220px
- Separator + gap: 24px + 24px before / 24px after
- Gated card: 320–360px (skeleton/seats-full ceiling)
- Page chrome bottom: 32px
- **Total at 768 viewport height with banner ON: ~700px** → fits at 768 with no scroll.

If the host theme injects extra chrome (`@blok/topbar` already accounts for ~56px), this fits comfortably. Mobile degrades to single-column scroll (see § 5).

### Key components and patterns

The gate's state machine renders **one shared frame** with **swappable inner content**. Adopters who replace `<PremiumContent>` in the allowed state don't touch denial states.

## 3. Key screens and flows

The gated section is **one card** with **one of 6 inner contents** at any moment: skeleton, allowed-welcome, no-subscription, seats-full, user-unassigned, error-fallback. The card frame, the eyebrow label "Premium," and the section's dimensions stay invariant — only the inner content swaps. This sameness eliminates layout shift on resolve (ADR-0007's whole point).

### 3.1 — Single-page freemium layout (Surface 1)

**Purpose:** Convey "top is free, bottom is gated" at first glance without copy reading.

**Composition:**

- `@blok/topbar` at the top edge. Display label: `"Paywall Blueprint"`. No nav links, no user menu, no tenant switcher in PRD-000 (those imply features the blueprint doesn't have).
- Centered content column, `max-w-[880px]`, `mx-auto`, `px-6` (24px horizontal padding per Blok spacing scale via `--spacing-6`).
- Top-padding `pt-6` (24px) between topbar bottom and free card.
- Free card sits at the top, separator below, gated card below that.
- Background: `bg-background` (Blok semantic token — adapts to host theme).

**Color treatment:**

- Cards use `bg-card` + `text-card-foreground` (default Blok `@blok/card` rendering).
- Section eyebrow labels use `@blok/badge` (small variant) — `Free` uses `variant="secondary"` (muted-foreground on muted background); `Premium` uses `variant="default"` (primary on primary-background). The badge difference is the second visual signal: muted = open access, vivid = gated. Reads at glance even when copy is muted.

**Visual notes:**

- Card elevation: `shadow-sm` only (per `sitecore:blok-theming` iframe shadow guidance — large shadows clip at iframe edges).
- Separator: full-width minus 32px gutters; uses Blok's `border-border` token via `@blok/separator`.

### 3.2 — Free section content (Surface 2)

**Purpose:** Demonstrate "this is a real feature" without actually being one (PRD R3).

**Composition:**

- `@blok/badge` (small, secondary) — text: `"Free"`
- `@blok/card` body with:
  - **Headline** — `text-xl font-semibold tracking-tight text-foreground` → `"Inventory at a glance"`
  - **Paragraph** — `text-sm text-muted-foreground leading-relaxed mt-2` → one paragraph (~140 chars):
    > `"This is where your free tier lives. Adopters of the blueprint replace this card with a real free feature — a counter, a status tile, anything that ships value without a paid plan."`
  - **Mock UI element** — a `@blok/button` (variant `secondary`, size `default`) — label `"View placeholder report"` — with `aria-label="Placeholder action — does nothing"` and a small `Lucide` `BarChart3` icon. Click is a no-op (the click-target maps in § 7 mark this as "non-interactive demo only").

**Copy rationale:**

- Headline 4 words, on the quality-bar's ≤6-word ceiling.
- Body 2 short sentences, on the ≤2-sentence ceiling.
- The phrase "adopters of the blueprint replace this card" is intentional: viewers of the demo video read the screen and understand the swap-point without consulting README.

**States:**

| State | Treatment |
|---|---|
| Default | As above |
| Button hover | Blok default — `bg-secondary/80` |
| Button focus | Blok default — `ring-2 ring-ring ring-offset-2` |
| Button disabled | N/A — button is always enabled (it's a demo placeholder) |

### 3.3 — Skeleton loading state (Surface 3)

**Purpose:** Occupy the gated subtree footprint while entitlement is pending. Sized to absorb the largest resolved state per ADR-0007.

**Composition (single generic skeleton):**

- `@blok/badge` placeholder — `@blok/skeleton` of width 56px, height 22px
- Icon placeholder — `@blok/skeleton` of width 32px, height 32px, `rounded-full`
- Headline placeholder — `@blok/skeleton` of width 240px, height 24px
- Body placeholders — two `@blok/skeleton` lines, full width and 80% width, height 16px each
- Two CTA-row placeholders (sized to two-button row of `tenant_active_seats_full`):
  - Primary CTA placeholder — `@blok/skeleton` of width 160px, height 36px, `rounded-md`
  - Secondary CTA placeholder — `@blok/skeleton` of width 140px, height 36px, `rounded-md`

**Vertical rhythm:** Same spacing as resolved states (gap-3 / gap-4 / gap-6 from Blok scale) so the swap is visually invisible.

**Motion:**

- Blok's built-in `animate-pulse` on `@blok/skeleton` primitives — no override.
- On resolve, the inner skeleton block fades to the resolved content over 200ms (`opacity` from 0.4 to 1 + `translateY(4px)` to `translateY(0)`). One transition only; respects `prefers-reduced-motion` (motion disabled when reduced-motion is set).

**No flash-of-allowed:** Skeleton is the gate's default render until BOTH `useAppContext()` returns non-null AND the entitlement promise resolves (per ADR-0008 + FR-1 steps 2 + 5). The architecture's defensive null-guard means the skeleton owns the void.

### 3.4 — Post-gate `allowed` welcome screen (Surface 4)

**Purpose:** Confirm "you have access" without overpromising features the blueprint doesn't have.

**Composition:**

- `@blok/badge` — small, default variant — text: `"Premium"`
- Icon — Lucide `CircleCheck` at 32×32, color `text-primary` (Blok semantic — adapts theme)
- Headline — `text-xl font-semibold tracking-tight text-foreground`:
  > Template: `"Welcome, {firstName}"`
  > With fallbacks per FR-9:
  >
  > - Priority 1: `context.user.name` → if multi-word, take first token; if single, use as-is → `"Welcome, Christian"`
  > - Priority 2: `context.user.email` → take everything before `@` → `"Welcome, christian.hahn"`
  > - Priority 3: literal `"there"` → `"Welcome, there"`
- Body — `text-sm text-muted-foreground leading-relaxed`:
  > Template: `"Your tenant {tenantName} has full access. Replace this card with your gated feature."`
  > With fallbacks per FR-9:
  >
  > - Priority 1: `context.tenant.name` → `"Your tenant Acme Inc. has full access. …"`
  > - Priority 2: `context.tenant.id` truncated to last 8 chars → `"Your tenant …5f3a-9c21 has full access. …"`
  > - Priority 3: literal `"your tenant"` → `"Your tenant has full access. …"` (no leading literal duplication — the `"Your tenant"` of the template absorbs the fallback)
- **No CTA.** The welcome state is recognition only. No action belongs here — adopters who plug in a real feature provide their own CTAs inside the swapped `<PremiumContent>`.

**Copy rationale:**

- Greeting verb-free; warmth comes from the name + tenant grounding, not from "Hooray!" framing.
- The second sentence "Replace this card with your gated feature." is a directional cue for forking adopters reading the live app — same intent as Surface 2's adopter cue.
- Headline ≤ 6 words (counting comma); body 2 short sentences.

**States:**

| State | Treatment |
|---|---|
| Default | As above |
| Focus (any embedded link / future CTA) | Blok `ring-2 ring-ring ring-offset-2` |
| Reduced motion | Skip the 200ms fade-in; render at final state immediately |

### 3.5 — `no_subscription` denial state (Surface 5)

**Purpose:** Warm "start your subscription / view plans" intent. No shame, no "denied" framing.

**Composition:**

- `@blok/badge` — small, default variant — text: `"Premium"`
- Icon — Lucide `CircleAlert` at 32×32, color `text-muted-foreground` (intentionally muted — this is informational, not destructive)
- Headline — `text-xl font-semibold tracking-tight text-foreground`:
  > **`"Start your subscription"`** — 3 words, verb-led, on quality bar.
- Body — `text-sm text-muted-foreground leading-relaxed`:
  > **`"Your tenant doesn't have an active plan yet. Pick a plan to unlock the premium section."`** — 2 sentences, ≤ 26 words.
- Primary CTA — `@blok/button`, variant `default`, size `default`:
  > **Label: `"View plans"`** — 2 words, verb-led, no "Click here" / no "Learn more."
  > **`href: "https://example.com/buy"`** (PRD-001 replaces with real Lemon Squeezy checkout URL).
  > Opens in new tab — `target="_blank" rel="noopener noreferrer"` — because the checkout flow leaves the Sitecore iframe and shouldn't navigate the parent.
  > Trailing icon: Lucide `ExternalLink` at 14×14, inherits `currentColor`.

**Copy rationale:**

- "Start your subscription" reads as forward motion (a beginning, not a wall).
- "Pick a plan to unlock the premium section" — verb-led, names what they get, no marketing-fluff adjectives ("amazing," "powerful").
- "View plans" rather than "Subscribe now" — viewer hasn't committed; the CTA invites browsing, not a commitment-shaped click.
- The plural "plans" hints at tier options without committing the blueprint to any specific plan structure.

**States:**

| State | Treatment |
|---|---|
| Default | As above |
| Button hover | Blok default — `bg-primary/90` |
| Button focus | `ring-2 ring-ring ring-offset-2` |
| Button active | Blok default — slight scale-down |
| Button disabled | Never disabled in PRD-000 |

### 3.6 — `tenant_active_seats_full` denial state (Surface 6)

**Purpose:** Convey "all seats used; admin can reassign or upgrade." Two CTAs — primary action + secondary message.

**Composition:**

- `@blok/badge` — small, default variant — text: `"Premium"`
- Icon — Lucide `Users` at 32×32, color `text-muted-foreground`
- Headline — `text-xl font-semibold tracking-tight text-foreground`:
  > **`"All seats in use"`** — 4 words, on quality bar.
- Sub-line / seat counter — `text-sm font-medium text-foreground mt-1`:
  > Template: `"{seatsTotal} of {seatsTotal} seats in use"` — e.g., `"5 of 5 seats in use"`. (`EntitlementResult.seatsTotal` is the only available numeric per FR-2; current usage equals total in this state by definition.)
- Body — `text-sm text-muted-foreground leading-relaxed mt-2`:
  > **`"Ask your team admin to reassign a seat, or upgrade your plan for more."`** — 1 sentence, 14 words, names both paths (admin reassignment AND upgrade).
- Primary CTA — `@blok/button`, variant `default`, size `default`:
  > **Label: `"Upgrade plan"`** — 2 words, verb-led.
  > **`href: "https://example.com/upgrade"`** (PRD-001 replaces).
  > `target="_blank" rel="noopener noreferrer"` + trailing `ExternalLink` icon.
- Secondary CTA — **none in PRD-000.** The body sentence carries the admin-reassignment message as text, not as a clickable element. Rationale: PRD-000 has no "notify admin" surface (deferred to PRD-002); a clickable "Ask admin" button with no destination would signal a broken pattern. The text-only mention preserves the no-shame, two-path framing without manufacturing a dead-end CTA.

**Copy rationale:**

- Headline avoids both "denied" and the punitive "FULL" framing — "in use" reads as descriptive, not blocking.
- Counter is plain-prose ("5 of 5") not a chip ("5/5") — better for screen readers and lower visual weight.
- "Ask your team admin to reassign a seat, or upgrade your plan for more." — the comma-pivot names BOTH paths in one sentence; the editor and the admin both have a next step.
- "Upgrade plan" rather than "Get more seats" — the editor encountering this might not have purchase authority, but the CTA targets the admin who does; "upgrade plan" reads as a path the admin understands.

**States:** Same as Surface 5.

### 3.7 — `tenant_active_user_unassigned` denial state (Surface 7)

**Purpose:** "Your admin hasn't given you access yet" — warm, names the admin role, no "Request seat" CTA in PRD-000 (deliberate per PRD US-3 — no disabled buttons).

**Composition:**

- `@blok/badge` — small, default variant — text: `"Premium"`
- Icon — Lucide `UserPlus` at 32×32, color `text-muted-foreground`
- Headline — `text-xl font-semibold tracking-tight text-foreground`:
  > **`"Ask your team admin"`** — 4 words, verb-led, on quality bar.
- Body — `text-sm text-muted-foreground leading-relaxed mt-2`:
  > **`"Your tenant has a plan, but your team admin hasn't given you a seat yet."`** — 1 sentence, 14 words, neutrally explains the situation.
- **No CTA in PRD-000.** Rationale: PRD-002 lands the "Request seat" notification flow; PRD-000 doesn't ship disabled-button placeholders. The single sentence carries the next-step verbally ("Ask your team admin") without manufacturing a click target.

**Copy rationale:**

- Heading and body together carry "the verb-led CTA": *Ask your team admin* — there's no button because the action lives outside the iframe.
- "hasn't given you a seat yet" — the word "yet" softens the state to temporary, not denied.
- The implicit ask-pattern aligns with the `no_subscription` denial pattern (Surface 5) but adjusted: instead of "Pick a plan," it's "Ask your team admin." Same visual structure, copy adjusted — adopters who fork inherit the parallelism.

**States:** Same as Surface 5 minus the button row.

### 3.8 — Demo-mode banner (Surface 8)

**Purpose:** Make `NEXT_PUBLIC_PAYWALL_ENABLED=false` visibly honest. Locked literal copy `"Paywall disabled — demo mode"` per FR-6 / ADR-0004.

**Composition:**

- `@blok/alert`, variant `default` (Blok's neutral informational variant — not destructive, not warning).
- Position: **top of page, immediately below `@blok/topbar`, full-width minus the page's horizontal gutters (24px).** Top placement makes it the first thing a demo-video viewer sees after the topbar; bottom placement risks clipping at iframe edges or being scrolled past.
- Icon: Lucide `Info` at 16×16, inherits alert's `currentColor`.
- Title: `"Paywall disabled — demo mode"` (locked literal per FR-6 + ADR-0004).
- Description: `text-xs text-muted-foreground`:
  > `"Set NEXT_PUBLIC_PAYWALL_ENABLED=true to evaluate entitlements."`
- **No dismiss button.** Per ADR-0004 the banner is non-dismissible per session — the signal must remain honest.

**Visual treatment for unmissability:**

- Default Blok alert is a subtle muted surface (`bg-muted` / `text-muted-foreground`). For demo-mode the spec leaves this default — the recurring presence is what makes it noticed, not visual aggression. A garish color would imply "warning / something is wrong"; the banner is informational, not corrective.
- Spacing below: 24px gap before free section starts.

**A demo-video viewer's perspective:** Even at 720p compressed video the title text "Paywall disabled — demo mode" reads at a glance (Geist Sans semibold at 14px → ~10px at 720p, still legible). The position above the free card means it's always in-frame whenever the page is.

**States:**

| State | Treatment |
|---|---|
| Default (flag === 'false') | Visible |
| Flag-on (default / 'true') | Banner NOT rendered |
| `prefers-reduced-motion` | No motion treatment; banner is static — no concern |

### 3.9 — Error boundary fallback (Surface 9)

**Purpose:** Render when the gate or its subtree throws. The free section above MUST keep rendering (NFR-6 + § 8.5 architecture).

**Composition:**

- The fallback replaces the **gated card content** only. The free card, separator, and demo-mode banner (if present) keep rendering normally — the error boundary scopes to the gated subtree per § 8.5.
- The gated card frame stays — same `@blok/badge "Premium"` eyebrow, same dimensions.
- `@blok/empty-states` primitive (or composed equivalent — `empty-states` is in Blok's data-display catalog).
- Icon — Lucide `TriangleAlert` at 32×32, color `text-muted-foreground` (intentionally muted — the user can't act on this; visual treatment should not amplify alarm).
- Headline — `text-xl font-semibold tracking-tight text-foreground`:
  > **`"Something went wrong"`** — 3 words, generic per NFR-6.
- Body — `text-sm text-muted-foreground leading-relaxed`:
  > **`"Please refresh the page or try again in a moment."`** — 1 sentence, 11 words.
- No CTA in PRD-000. Rationale per FR-1: "PRD-000 deliberately does not implement an in-gate retry UX; PRD-001 will introduce explicit provider-unreachable UX with retry logic." A refresh prompt covers the broken-context and broken-store cases generically.
- Error boundary logs `[PaywallBlueprint] <error>` to `console.error` per NFR-6 (visual: nothing).

**Copy rationale:**

- "Something went wrong" — the only acceptable generic for an unrecoverable client-side fault. Avoids both "Oops!" (too cute) and "Error 500" (too technical).
- "Please refresh the page or try again in a moment" — gives the user a concrete action without promising a retry button.

### 4.7 — Accessibility notes

- **WCAG AA contrast** verified at runtime against Blok tokens (per NFR-2). Spec relies on Blok's token contrast guarantees; QA verifies in both `.dark` and light themes.
- **Focus order** — Tab sequence on a happy-path render (allowed state): topbar (if focusable items added later) → free section button → (gated section has no focusable elements in allowed state) → demo banner (if present, non-focusable). Tab sequence on `tenant_no_subscription`: free section button → "View plans" button → (end). Tab sequence on `tenant_active_seats_full`: free section button → "Upgrade plan" button → (end). Tab sequence on `tenant_active_user_unassigned`: free section button → (end — no gated focusables).
- **Focus rings** — Blok `ring-2 ring-ring ring-offset-2` on all interactive elements. Visible in both themes.
- **Reduced motion** — `prefers-reduced-motion: reduce` disables the 200ms skeleton-to-resolved fade and translate. Static swap renders immediately. Skeleton's `animate-pulse` is suppressed under reduced-motion per Blok defaults.
- **Screen reader cues:**
  - Free section card: `role="region" aria-labelledby="free-section-heading"`.
  - Gated section card: `role="region" aria-labelledby="gated-section-heading"` (headline ID swaps per state).
  - Skeleton state: wrap in `role="status" aria-live="polite" aria-label="Loading premium content"` so screen readers announce loading; on resolve, the announcement replaces with the new content.
  - Demo banner: `@blok/alert` already carries `role="alert"`; screen readers announce on render.
  - External-link CTAs (Surfaces 5, 6): `aria-label="View plans (opens in new tab)"` / `aria-label="Upgrade plan (opens in new tab)"`.
  - Mock free-section button: `aria-label="Placeholder action — does nothing"` so non-sighted users understand it's a demo placeholder.
- **No emoji codepoints used for state icons.** All state icons are Lucide-react entries inheriting `currentColor` from Blok semantic tokens per `sitecore:blok-theming` "Color-emoji codepoints" note. Verified glyph list: `BarChart3`, `CircleCheck`, `CircleAlert`, `Users`, `UserPlus`, `Info`, `TriangleAlert`, `ExternalLink`. None are emoji.

## 5. Responsiveness and accessibility

### 5.1 — Breakpoints

Per `sitecore:blok-marketplace-integration`: iframe viewport is 1024–1920px × 600–1080px. The design's primary target is desktop ≥1024 wide.

| Breakpoint | Behavior |
|---|---|
| ≥1024px (Marketplace default) | Centered 880px column; cards full-width within. Both sections + banner fit at 768 viewport height. |
| 768–1023px (worst-case Marketplace iframe per source command) | Same single-column layout; column width = `100% - 48px` gutters; still fits without scroll at 768 height. |
| 480–767px (mobile, rare for Marketplace) | Single-column scroll; topbar collapses per `@blok/topbar` defaults; gated card may push below the fold and become scroll-revealed. Acceptable degradation — Marketplace apps are not mobile-targeted. |
| 360–479px (very small mobile, very rare) | Same single-column scroll; CTAs become full-width (`w-full`); button labels wrap if needed. |

**No tablet-specific layout** — the iframe rarely lands there; the 1024 desktop layout degrades cleanly via the same single-column composition.

**Container queries** considered but not needed — the iframe parent width is the only relevant dimension, and the page's max-width clamp handles it.

### 5.2 — Accessibility requirements summary

- **WCAG AA** across all surfaces (NFR-2).
- **Keyboard navigation** — every interactive element reachable via Tab; focus order matches visual order (top-to-bottom).
- **Visible focus rings** — Blok `ring-ring` token; passes contrast in both themes.
- **Screen reader announcements** — region roles + `aria-labelledby`; loading state uses `aria-live="polite"`; external-link CTAs declared "(opens in new tab)" in `aria-label`.
- **Reduced motion** — respected via `prefers-reduced-motion` media query; the spec's only motion (200ms skeleton fade) is gated.
- **Color independence** — no information conveyed by color alone. Section identity uses **badge label text + position + separator**, not just badge color. Denial vs allowed states distinguished by **icon glyph + headline text**, not just icon color.
- **Touch targets** — all interactive elements ≥40×40 (Blok button defaults satisfy this).
